# Правила арены

Сначала прочитай README.md. Затем применимые common/ и промпт своей роли.

- В Markdown каждый абзац пиши в одну физическую строку, без ручных переносов по ширине или после каждого предложения. Абзацы разделяй пустой строкой; перенос по ширине окна оставляй редактору. Структурные переносы в списках, таблицах и блоках кода сохраняй.
- Отчёты разработки сохраняй в `archive/development/`, исторические отчёты и свидетельства кейсов — в `archive/cases/`. Не добавляй их в `common/` или обязательный стартовый контекст; архив читается по отдельной задаче.
- Арена универсальна: задача, метрика, разрешённые изменения решения, харнеса и его параметров задаются файлами кейса и промптом кампании. Не добавляй зависимость от конкретного харнеса или домена в общий протокол.
- Подготовка и поиск — отдельные запуски по команде пользователя. Агент подготовки выполняет prompts/prepare.md и common/preparation.md, сохраняет готовый пакет и условия, затем завершает работу. Поисковый запуск по prompts/start.md проверяет готовность и использует эти результаты; при незавершённой подготовке сообщает о пробелах и завершается, не запуская подготовку автоматически.
- Делегируй независимые направления исследователям в отдельных worktree. Следуй common/orchestration.md и common/IMMUNE.md.
- Не меняй зафиксированные условия, модель, метрику, эталоны и split внутри кампании. Харнес и его параметры могут быть фиксированными или переменными поиска согласно промпту.
- Решатель и метрика могут работать без LLM. Все модельные обращения с данными идут только к внутренним моделям; если решатель и судья используют LLM, их модель одна и та же.
- Один корректно полученный ответ на пример. Процедуру оценки и число судейских голосов задаёт зафиксированная метрика; у встроенного профиля llm поле votes по умолчанию равно 3. При ошибках модельного запроса — до пяти повторов с прежними входом и настройками; валидный ответ ради балла не повторяется.
- Единственный лимит поиска — число предложенных решений. Каждая версия, включая неудачные, расходует одно место; технический повтор прежнего запроса не создаёт новое решение. Токены и время измеряются, но не ограничивают поиск.
- При явной команде человека остановить поиск не начинай новые проверки: дождись только уже выполняющихся и выбери финалистов по накопленным свидетельствам.
- Размер входа private и число итоговых решений задаются отдельно и точно. Планируй воронку под эти числа; выбирай входной набор по качеству и полезности, а не только по баллу.
- Train открыт для замеров, подвыборок и анализа трейсов. Public может возвращать агенту только общий score. Private не возвращает агенту результаты, включая итоговые оценки. Train и public могут быть пустыми.
- Токены и время решения измеряй обязательно, включая подготовку и повторы; затраты оценщика храни отдельно. При равном балле применяй правило common/public-evaluation.md.
- Сохраняй родословную, неизменяемые версии всех решений и измерения для кривой эволюции и AUC по common/search-history.md. Неудачное решение может иметь потомков.
- Долгие задания и субагентов жди по common/long-runs.md: проверь первый результат, рассчитай остаток и ожидай весь срок без промежуточного опроса моделью.
- Новые private-попытки не открываются переименованием кампании или кандидата.
- Отрицательные результаты сохраняй вместе с гипотезой и числами. Никогда не сохраняй секреты или закрытые данные в Git, образах и общем MLflow.
- Для детерминированного кода сначала тест; для качества сначала критерий и измерение. Не запускай реальные модели без задачи на эксперимент и зафиксированного числа решений.
- Не добавляй контрольные суммы файлов и инструкции по их проверке без явного запроса пользователя.
- Перед передачей изменений: uv run ruff check ., uv run pyright, uv run pytest и uv run python -m evaluator.smoke.
