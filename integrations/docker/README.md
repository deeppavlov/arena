# Монитор Docker-исследователя

Необязательная интеграция для кампаний, где внешний исследователь выполняется в Docker. Она не определяет кейс, харнес, модель или метрику.

```bash
uv run python -m integrations.docker.research_monitor watch --config /path/to/monitor.json
```

Оператор передаёт конфигурацию `Settings`: пути к `active_file`, `usage_dir`, `trace_dir`, `state_dir`, метаданные `params` и списки `shared_queues`/`operator_queues`. Launcher записывает ID запуска gateway и полный ID контейнера в `active_file`. Монитор читает состояние этого контейнера, дожидается завершения модельных запросов, сохраняет итоговый учёт и экспортирует запись. Поиск он не запускает и не перезапускает.

Для экспорта настраиваются `MLFLOW_TRACKING_URI` и `ARENA_OPERATOR_MLFLOW_TRACKING_URI`; SDK устанавливается через extra `tracking`. Очереди доставки сохраняются при ошибке. Docker socket и операторские каталоги доступны только доверенному монитору, не исследователю.

Для монитора задавай `MLFLOW_ENABLE_ASYNC_TRACE_LOGGING=false` до запуска процесса. Он и так подтверждает каждый вызов перед следующим; синхронный режим избегает секундного ожидания очистки асинхронной очереди MLflow 3.16.0 на каждом вызове. Payload и подтверждение доставки сохраняются. Изменение переменной после инициализации SDK не переключает уже созданный экспортёр.

После аварийного завершения gateway сохранённый счётчик активных запросов может требовать операторского восстановления. Монитор не обнуляет его по таймауту и не выдаёт неизвестный расход за нулевой.

Gateway сохраняет попытку с неизвестным расходом до обращения к модели, затем дополняет её фактическим usage. Если первая запись невозможна, модель не вызывается. Если сохранение результата учёта не удалось, попытка остаётся в `unreported_attempts`; gateway возвращает ошибку без повторного модельного вызова. Отсутствующий трейс такой попытки даёт `trace_complete=false`, даже если ни одного вызова не удалось сохранить. Значения токенов при неполном учёте остаются нижней границей расхода.

Итог записывается в `state_dir/records/<run_id>.manifest.json`: учёт, статус контейнера, исходные времена и список `call_files`. Монитор читает каждый исходный JSON вызова по отдельности; он не собирает полный многодневный трейс в памяти. Память зависит от крупнейшего отдельного вызова и списка путей, а не суммы содержимого всех вызовов. Исходные файлы gateway сохраняются неизменяемыми. Экспортёр делает собственные очищенные снимки вызовов в очереди и публикует их отдельными MLflow-трейсами внутри одного run. Сохраняются полный payload, исходные времена и роль `orchestrator`; сокращения содержания нет.

Очереди этого формата находятся в `state_dir/manifest-queues/shared` и `state_dir/manifest-queues/operator`. `progress.json` отдельно показывает завершение исследователя и результат доставки каждому получателю. `finished` не означает, что доставка уже завершилась: оба настроенных получателя должны вернуть `exported`. Поле `trace_complete` показывает, совпало ли число локальных вызовов со счётчиком попыток gateway.

## Восстановление после OOM старого экспортёра

Обнови вместе монитор и `evaluator.tracking` в доверенном окружении. Сохрани прежние `active_file`, `usage_dir`, `trace_dir`, `state_dir` и завершённый контейнер исследователя: его состояние нужно для подтверждения исходного результата и времени. Затем выполни:

```bash
uv run --extra tracking python -m integrations.docker.research_monitor once --config /path/to/monitor.json
```

Монитор создаст компактный manifest из существующих вызовов и учёта. Старые монолитные `records/<run_id>.json` и `queues/` остаются нетронутыми и автоматически не читаются. Доставка manifest создаёт отдельную запись MLflow; прежняя `FAILED` остаётся свидетельством сорванного экспорта. Не добавляй старые очереди исследователя в `shared_queues` или `operator_queues`: их повторная загрузка сохраняет прежний риск OOM. Эти списки продолжают обслуживать явно настроенные очереди проверок.

При временном сбое доставки повтори `once` либо запусти `flush --config /path/to/monitor.json`; очереди содержат снимки и подтверждения отдельных вызовов. Сопоставь `orchestrator_trace_attempts` с `orchestrator_attempts` и дождись `exported` у настроенных получателей. Повтор не запускает исследователя, решения, модели, оценку или новую private-попытку. Если завершённый контейнер уже удалён, не подставляй его статус: сначала восстанови подтверждённое операторское свидетельство; имеющихся вызовов недостаточно для определения кода завершения процесса.
