# Метрика SC-71

Пакет фиксирует принятую метрику исходного набора из 100 примеров: полнота — 0,35, точность — 0,35, обоснованность — 0,30. Единственный итоговый ответ на пример получает по три независимые целые оценки 1–5 каждого критерия. Код усредняет голоса и складывает критерии с указанными весами. Модель и reasoning effort закреплены в `policy.json`.

Итог примера находится в диапазоне 0–5. Ноль ставится за пустой ответ, ответ на неответимый вопрос без маркера отказа или ссылку на несуществующий документ KB. Неверная цитата, ложный отказ на ответимый вопрос и неверный JSON не добавляют новых правил обнуления: они отражаются в диагностике и оценках критериев. Ошибка судьи, потерянный голос, повреждённый эталон или недоступный корпус останавливают измерение с ошибкой и не превращаются в нулевой score.

Агрегатор усредняет средние оценки тем T1–T5 с равными весами. Полные train, public и private должны содержать все пять тем. Для разведочной train-подвыборки усредняются только присутствующие темы; отсутствующие темы не заменяются нулём. Сопоставлять следует одинаковые наборы ID при одинаковых условиях.

## Операторские входы

`ARENA_SC71_KB_ROOT` указывает на замороженный исходный корпус, содержащий `norm/<origin_id>.md`. Это корпус для проверки цитат, независимо от представления KB, которое создал кандидат. Отсутствие документа эталона или исходной цитаты — ошибка конфигурации. Пути документов не могут выходить из `norm/` через symlink. Версия корпуса фиксируется в manifest кампании, отдельно от пакета метрики.

`Example.input` содержит исходную общую инструкцию задачи, два перевода строки и текст вопроса. `Example.reference` — JSON-строка следующего формата:

```json
{
  "format": "sc71-reference-v1",
  "topic": "T1",
  "reference_markdown": "Принятый исходный Markdown-эталон",
  "gold": {"topic": "T1", "answerable": true}
}
```

В примере показана только форма оболочки. `gold` содержит весь исходный структурный эталон, включая `citations`, `must_include`, `must_not_include` и данные темы. Исходные MD/JSON не генерируются заново и не корректируются метрикой. Они хранятся только в разрешённом контуре соответствующего split.

Судья получает вопрос, принятый Markdown-эталон, ответ, один критерий, результаты программных проверок и перечисленные в эталоне цитаты, найденные в исходном корпусе. Цитаты передаются в фактическом написании корпуса. Тексты корпуса вне этих участков, история кампании, чужие голоса и веса критериев судье не передаются.

## Программные проверки

Ссылки извлекаются из `/kb/norm/<64hex>.md`. Регистр hex несущественен; повторные ссылки на один ID считаются один раз. Для recall/precision и проверок T3–T5 учитываются перечисленные `equivalent_origin_ids`.

`citation_recall` измеряет долю обязательных документов; для T3 используются документы шагов. Повтор одного и того же набора эквивалентных документов не увеличивает знаменатель. `citation_precision` — доля процитированных документов из primary, supporting и superseded эталона; near_miss в это множество не входит. На ответимом примере отсутствие ссылок даёт precision 0; на неответимом оба показателя равны `null`. Ответимый эталон без обязательных документов — ошибка.

`fabricated_quote` проверяет цитаты длиной не менее 20 нормализованных символов по полному тексту всех процитированных документов. При сравнении схлопываются пробелы и игнорируется регистр; OCR и буквы не исправляются. Поддерживаются кавычки «…», “…” и обычные двойные. В JSON ключи и произвольные строковые значения не считаются цитатами: проверяются поля `quote`, `цитата`, `citation_quote` и фрагменты в типографских кавычках внутри строк.

Отказ распознаётся только в первой непустой строке. Пробелы, регистр и завершающая точка несущественны. Остальные проверки сохраняют исходный смысл метрики: вхождения обязательных/запрещённых строк, ошибка обновления T1, тип коллизии и применимая норма T4, попадание в целевой документ T5. JSON T4 должен быть одним объектом, возможно внутри единственного блока Markdown; частичные или несколько объектов не принимаются. При `applicable=both` достаточно одной из двух норм, как определено исходной метрикой.

`statistics` содержит только тему, числа, булевы признаки и численные голоса. В нём нет вопросов, ответов, цитат, ID документов или обоснований судьи. Исходные закрытые данные остаются у оценщика и внутренней модели. Usage хранится по общему протоколу; наружу public отдаёт только общий score, private — только статус.

## Повторы и таймауты

Модельные запросы идут только через выданный внутренний gateway. Параметр `response_schema` передаёт gateway строгую схему оценки: целое `score` 1–5 и непустой `reason`, без дополнительных полей. Gateway проверяет схему внутри единого лимита исходной попытки и пяти повторов, удаляя служебную схему перед обращением к модели. Скрипт не добавляет SDK-повторов или своего цикла ретраев. Оператор берёт неизменную схему из `score.py:SCORE_SCHEMA` и добавляет её в `MODEL_RESPONSE_SCHEMAS_JSON` доверенного gateway. Каждый голос передаёт локальные `trace_metadata` с ролью, критерием и номером голоса. Gateway сохраняет их в `attributes.caller_metadata` как недоверенные метки и не отправляет модели.

Ожидание HTTP-запроса берётся из `model_request_timeout`. Девять последовательных запросов при стандартных 130410 секундах требуют до 1173690 секунд; таймаут всей команды составляет 1209600 секунд, или 14 суток. Это аварийные технические пределы, а не ограничения времени поиска. Usage и длительность оценки учитывает gateway и evaluator отдельно от решателя.

Проверки `tests/test_sc71_metric.py` используют вымышленные документы и подставные модельные ответы. Реальных данных и обращений к модели в них нет.
