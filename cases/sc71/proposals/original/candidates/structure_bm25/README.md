# Структурный поиск по документам

Новый самостоятельный кандидат `structure_bm25`, 16.10.2026. Существующие
`bm25_sections`, `hybrid_bge`, `linked_hybrid`, общий `src/sc71.py` и старые результаты
не изменяются. Измерение качества этого кандидата на SC-71 ещё не выполнено.

## Что делает

1. По заголовку эвристически выбирает профиль: приказ, положение/регламент,
   договор либо общий текст. Это не юридическая классификация.
2. Создаёт дерево документа, разделов и нумерованных пунктов. Подпункт `1.2`
   становится ребёнком существующего пункта `1`. Отдельные номера страниц и даты
   не считаются пунктами. Для общего текста используются абзацы и ограниченные окна.
3. Выделяет обычные Markdown-таблицы и строки с несколькими табуляциями.
   Исходные таблицы из повреждённого OCR автоматически не восстанавливает.
4. Индексирует исходный текст листьев тем же BM25, что и сохранённая база сравнения.
5. Внутри найденного пула немного повышает позиции совпадений с путём заголовков.
6. Возвращает целый подходящий пункт, небольшой родительский пункт либо соседние
   пункты в пределах того же раздела. Для длинной таблицы добавляет исходный заголовок
   отдельным доказательным участком. При нехватке бюджета возвращается к исходному
   найденному фрагменту, не обрезая и не переписывая цитату.

Границы листа — до 1800 символов, расширенный участок — до 3600, соседство — 1 пункт,
вес совпадения заголовка — 0.15. Итог: максимум 8 участков, 3 на документ, 16000
символов текста и шапок документов. Шапка до 400 символов учитывается для каждого
участка, как в исходном кандидате. Это бюджет текстов, не всех JSON-полей и не токенов.
Стартовые параметры не подбирались по Public-ответам.

## Начать с искусственного примера: без модели

Git Bash, из корня `deus-ex-harness`, с активированным Python-окружением:

```bash
export PYTHONUTF8=1
WORK=artifacts/SC-71/kryukova
C="$WORK/candidates/structure_bm25"
python -B "$C/build.py" --kb-dir "$C/examples/norm" \
  --build-dir "$C/checks/demo-index-v1"
python -B "$C/run.py" --build-dir "$C/checks/demo-index-v1" \
  --question 'Кто согласует приобретение оборудования?' --format json
```

Каждая сборка требует пустой/новый каталог. Старый индекс не перезаписывается.
Для переноса используйте `scripts/export.py`: он включает выбранного кандидата
и нужную версию `retrieval/`; импорт из исходной рабочей папки не требуется.

## Настоящий корпус и ответ GLM

Следующие команды показывают отдельный реальный запуск; в ходе реализации они
не выполнялись. Реальный вызов модели и размер прогона согласуются отдельно.

```bash
INDEX="$WORK/indexes/structure-v1"
python -B "$C/build.py" --kb-dir "$WORK/data/normalized/norm" --build-dir "$INDEX"

# Только поиск, без обращения к GLM:
python -B "$C/run.py" --build-dir "$INDEX" \
  --question 'Кто согласует закупку?' --format json

# Полноценный ответ: один вызов модели, указанной в существующем .env:
python -B "$C/run.py" --build-dir "$INDEX" --env-file "$WORK/.env" \
  --question 'Кто согласует закупку?' --answer-mode llm
```

`.env` явно передаётся через `--env-file`; автоматически файл из чужого проекта
не ищется. Читаются только переменные `SC71_*`, строки не исполняются как shell.
Используются `SC71_CHAT_URL`, `SC71_CHAT_MODEL`, при необходимости `SC71_CHAT_KEY`.
Имя модели не закреплено на DeepSeek. Публичные произвольные model endpoints
блокируются; сохранён допуск к согласованному лабораторному chat endpoint.

Генерация: прежние prompt и проверка цитат из единого общего движка. По умолчанию
`llm`, timeout 600 с, max_tokens 8192, если явно не задан `SC71_CHAT_MAX_TOKENS`.
`--answer-mode extractive` выдаёт только выдержки и не считается полноценным Q&A.
Ошибка проверки цитаты сохраняет полученный текст в stdout, выставляет статус
`answer_validation_failed` в stderr и код завершения 2. Ответ не перегенерируется.

## Выход и координаты

`--format json` выдаёт один retrieval JSON. В `hits` есть `origin_id`, `chunk_id`,
`span_id`, `char_start`, `char_end`, `line_start`, `line_end`, `quote`, `metadata`.
Для сохранения вывода можно перенаправить stdout и stderr в отдельные локальные файлы.

- Символьные позиции: Python Unicode после удаления UTF-8 BOM, от нуля;
  `char_end` не включён. CRLF сохранены, нормализация OCR не выполняется.
- Номера строк — от единицы, обе границы включены.
- `quote` точно равен `source[char_start:char_end]`.
- `chunk_id` — ID найденного листа; `seed_char_*` — его координаты.
  Восстановленный контекст и заголовок таблицы могут ссылаться на один лист;
  возвращённые исходные участки различаются по `span_id`.
- `metadata_spans` указывает, откуда взяты эвристические реквизиты. Они не
  доказывают действие документа или правильность распознавания его типа.
- `source_relpath` — имя Markdown относительно фактического каталога `norm`.
  `/kb/norm/...` в `citation` — прежнее условное обозначение источника,
  оно не создаёт папку `kb` на компьютере.

stdout содержит результат или ответ; stderr — одну диагностическую JSON-запись
без ключа и текстов найденных документов. Сам retrieval JSON/ответ может содержать
клиентский текст и наследует ограничения корпуса. Runtime читает индекс через
SQLite `mode=ro` и не пишет в пакет, корпус или индекс. `SC71_VERIFY_BUILD=1`
дополнительно проверяет хеши индексных файлов; на полном индексе это стоит времени.

## Абляции и ограничения

На одной сборке доступны `--no-expand` и `--no-heading-bonus`. Сначала сравните
старый BM25 с новой нарезкой при отключённых двух добавках; затем включайте
каждую добавку отдельно. У старых кандидатов ничего менять не нужно.

Приказ, положение и договор сейчас используют общую стратегию нумерованных
пунктов; отдельного тонкого алгоритма для каждого из этих трёх видов ещё нет.
От неё отличается fallback общего текста с абзацами, а таблицы обрабатываются
отдельно. Определение вида документа остаётся эвристикой.

Пропущенная нумерация, много актов внутри одного файла, OCR-таблицы и длинные
строки ограничивают точность дерева. Родительский контекст может дать шум.
Условие «самый свежий акт действует» не используется. Граф отмен, поиск по
произвольным метаданным и восстановление исходных страниц/bbox не реализованы.

`candidate.json` — локальный build/run descriptor с явными контейнерными путями,
аналогичный старым экспериментальным пакетам. Это не адаптер текущей Arena:
её JSON stdin/stdout и `prompt.md`/`prepare.py` требуют отдельной согласованной
интеграции по актуальному контракту. Сквозной тест Arena не заявлен.

Проверка кода:

```bash
python -B -m pytest "$C/tests" -q -p no:cacheprovider \
  --basetemp "$C/checks/my-tests-v1"
```

`verify.py` дополнительно проверяет второй новый пакет, старые тесты и корневой
проект; его запускают в исходной рабочей копии. Результаты: `checks/VALIDATION.md`.
