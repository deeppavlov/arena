# Поиск по плану

Новый самостоятельный кандидат `planned_bm25`, 16.10.2026. Старые кандидаты,
`public_bm25.py`, пользовательский `.env`, корпус, split и прежние прогоны
не изменяются. Качество на настоящем SC-71 этим пакетом ещё не измерено.

## Алгоритм

1. Один запрос к GLM получает только текущий вопрос и возвращает до трёх поисковых
   подвопросов. Корпус, найденные тексты и эталоны планировщику не передаются.
2. Исходный вопрос всегда остаётся первым поисковым запросом.
3. Новый номер или дата в подвопросе приводят к явной ошибке планировщика.
   Недостающие числовые реквизиты исходного вопроса возвращаются в каждый подвопрос.
   Одинаковые подвопросы удаляются, чтобы не получать повторные голоса RRF.
4. Для каждого запроса выполняется исходный BM25 по 48 кандидатам. До четырёх
   списков объединяются RRF с константой 60; общий пул после слияния — до 48.
5. В ответ передаётся до 8 исходных фрагментов, до 3 на документ, до 16000 символов
   вместе с шапками. Поисковые формулировки не становятся доказательствами.
6. Общий генератор даёт ответ по тем же правилам и prompt, что у остальных кандидатов.

Это наша проверяемая адаптация декомпозиции вопроса, а не полное воспроизведение
Chain of Logic или HyPA-RAG. Обученный классификатор, dense-поиск и knowledge graph
из HyPA-RAG здесь не используются. BGE и GPU не требуются.

## Файлы и зависимости

`candidate.py` — планировщик, защита реквизитов, BM25 и RRF; `common.py` — CLI,
лимиты и упаковка доказательств; `baseline.py` — совместимый импорт общего движка из `retrieval/`.
`build.py`/`run.py` сохраняют прежний CLI; переносимую поставку собирает `scripts/export.py`.
Runtime — Python 3.12, только стандартная библиотека. `requirements-dev.txt`
фиксирует прямые версии pytest/Ruff/Pyright; полный транзитивный lock не заявлен.

## Запуск

Git Bash, из корня проекта, с активированным Python-окружением:

```bash
export PYTHONUTF8=1
WORK=artifacts/SC-71/kryukova
C="$WORK/candidates/planned_bm25"
INDEX="$WORK/indexes/planned-v1"
python -B "$C/build.py" --kb-dir "$WORK/data/normalized/norm" --build-dir "$INDEX"

# Только поиск, но с ОДНИМ запросом к планировщику:
python -B "$C/run.py" --build-dir "$INDEX" --env-file "$WORK/.env" \
  --question 'Как согласовать приобретение оборудования?' --format json

# Планирование и итоговый ответ: обычно ДВА модельных запроса:
python -B "$C/run.py" --build-dir "$INDEX" --env-file "$WORK/.env" \
  --question 'Как согласовать приобретение оборудования?' --answer-mode llm
```

Эти реальные команды в ходе реализации не выполнялись. Модельные прогоны,
разрешённые Public-ID и бюджет согласуются отдельно; Private не используется.
Имя отвечающей модели и планировщика берётся из `SC71_CHAT_MODEL`, адрес — из
`SC71_CHAT_URL`, ключ при необходимости — из `SC71_CHAT_KEY`. Смена `.env` не
требует правки кода. Секреты в настройках пакета не сохраняются и не печатаются.

Планировщик: temperature=0, max_tokens=4096, timeout=600 с, reasoning_effort=low.
Последний параметр выбран для согласованной GLM-5.3-Flash; его поддержку на
лабораторном развёртывании ещё предстоит проверить. Для другого согласованного
сервиса его можно явно установить в `null` в новых settings до сборки и зафиксировать
это как другую конфигурацию. Автоматического изменения параметров при ошибке нет.

Одна корректная плановая генерация не повторяется ради лучшего поиска. Для
холодного HTTP 503 с Retry-After сохранены только ограниченные технические повторы.
Невалидный JSON, выдуманные числа, отсутствие модели и обрыв ответа — ошибка с
кодом завершения 2, без скрытого перехода в обычный BM25. Диагностика сохраняет
фазу, число логических вызовов, известные usage и хеш ответа; ключ и сырой ответ
планировщика не печатаются в диагностический журнал.

## Проверить без модели на искусственных данных

```bash
python -B "$C/build.py" --kb-dir "$C/examples/norm" \
  --build-dir "$C/checks/demo-index-v1"
python -B "$C/run.py" --build-dir "$C/checks/demo-index-v1" \
  --question 'Кто согласует приобретение оборудования и когда публикуются сведения?' \
  --plan-file "$C/examples/synthetic-plan.json" --format json
```

План в этом примере создан вручную для синтетических документов. Он проверяет
только алгоритм/формат, не качество GLM. Его нельзя считать настоящим прогоном
планировщика. В `tests/test_planned_runtime.py` весь процесс дополнительно проверяется
на скопированном пакете через синтетический loopback HTTP-сервис.

## Кэш и абляции

- `--no-plan --format json` — обычный BM25 без модельного вызова. Это явно
  обозначенная абляция, а не полноценное исполнение планового метода.
- `--plan-file` читает сохранённый объект `plan` из retrieval JSON. Он привязан
  к SHA256 вопроса и версии prompt. Сохраняйте происхождение плана и его модель;
  нельзя делать план из эталона. Повторное использование не вызывает GLM.
- `settings.single-query-control.json` увеличивает BM25-пул до 192. Соберите
  отдельный индекс с этим файлом и выполните `--no-plan`: это контроль, не
  объясняется ли эффект просто большим числом просмотренных кандидатов.
- Используйте одну и ту же модель, prompt ответа, top_k и бюджет контекста у всех
  систем. Затраты планировщика и генератора учитываются отдельно, цена неизвестна
  без ставок. Время поиска включает планировщик, если он вызывается.

Пул и модельные расходы не выдаются за одинаковые с исходным BM25: у планового
метода до четырёх поисков и один дополнительный модельный вызов.

## Выход и ограничения

`--format json`: один JSON с `hits`, `queries`, `plan`, usage/параметрами планировщика,
числом поисков, бюджетом контекста и отпечатками кода/сборки. stdout в режиме
ответа содержит сам ответ. stderr — одна диагностическая JSON-запись без цитат
и ключа. Ошибочный по цитатам ответ сохраняется в stdout с неуспешным статусом
и exit code 2; новый ответ автоматически не генерируется.

Координаты: символы Python Unicode от нуля после удаления BOM, конец не включён;
CRLF сохранены; строки от единицы. `source_relpath` — имя файла относительно
настоящего `norm`. `/kb/norm` в цитате — условный адрес, папка не создаётся.
Индекс открывается read-only. Эталоны и датасет не являются входами пакета.

Защита чисел не предотвращает все смысловые домыслы: GLM может неправильно выбрать
части вопроса или придумать ненужный орган согласования. RRF может повысить шум.
Новые редакции, юридический статус документа и отсутствие ответа этот метод сам
по себе не устанавливает. Успешная проверка цитат не доказывает верность вывода.

`candidate.json` — локальный build/run descriptor, не готовый адаптер актуальной
Arena. Её изолированное JSON-исполнение, assets и `prepare.py` потребуют отдельной
интеграции. Сеть и допуск модели определяет оператор; сквозной тест Arena не пройден.

Проверка:

```bash
python -B -m pytest "$C/tests" -q -p no:cacheprovider \
  --basetemp "$C/checks/my-tests-v1"
```

Источники и план измерения — `RESEARCH.md`; фактические проверки реализации —
`checks/VALIDATION.md`.
