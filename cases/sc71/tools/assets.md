# Материалы и измеряемая подготовка метода

SQLite/BM25, embeddings корпуса, деревья каталогов, тематические разделы, README,
реестры, графы и другие представления KB создаются в ходе поиска. Подготовка арены
размещает только исходную Paddle KB и инфраструктуру. Для построения представления
используется `build.py` зарегистрированного неизменяемого кандидата; обычная
публикация готовых файлов не заменяет измерение сборки.

Эта инструкция описывает локальную версию протокола после разделения кейса и ядра. Работающий GPU6 использует прежний пакет и прежние пути; его квитанции и состояние не мигрируются. Для новой установки поддержка build и выбора assets явно включается профилем SC-71, как описано в [развёртывании](../deploy/gpu6/README.md).

## Два способа подготовки

Общая для всех вопросов обработка KB выполняется один раз доверенным build-сервисом.
Он получает снимок кандидата из журнала, исходную KB и закреплённые зависимости,
запускает `build.py` в изолированном runner и публикует результат вместе с
доверенной квитанцией затрат. Вопросы, эталоны, split и ответы решателя в этот
запуск не передаются. `build.py` не генерирует окончательный ответ Hermes.

Подготовка, зависящая от текущего вопроса, может оставаться в `prepare.py` или
инструментах Hermes. Она выполняется внутри каждого измеряемого примера и уже
входит в его расходы. Файловому методу, читающему исходные Markdown без общей
сборки, `build.py` не нужен. Перенос сборки индекса в `prepare.py` допустим, но
тогда фактическая повторная сборка учитывается для каждого примера.

Обычный publisher служит для загрузки предобученных весов, библиотечных зависимостей
и разрешённых исходных материалов. Нельзя публиковать через него заранее
построенные индексы, embeddings KB, её пересказы, README или иные преобразованные
представления с последующим нулевым учётом их создания. Проверка publisher
подтверждает байты и пути, но не определяет семантическое происхождение файлов;
соблюдение этого ограничения дополнительно проверяется при ревью кандидата.

Перед загрузкой embedding/reranker-модели проверь требования и доступные RAM,
VRAM, CPU и диск GPU6. Зафиксируй версию весов и зависимости. Доступ к GPU не
назначается автоматически. Все генеративные обращения при сборке идут только
через выданный внутренний gateway с моделью и параметрами кампании.

## Журнал и неизменяемый рецепт

Единый журнал кампании расположен по логическому пути
`cases/sc71/campaigns/sc71-first-20261019/search.sqlite3` из `/workspace`. При подготовке оператор
один раз инициализирует его:

```bash
python -m evaluator.search \
  --journal cases/sc71/campaigns/sc71-first-20261019/search.sqlite3 \
  init --max-solutions 100
```

Готовность первого запуска требует `max_solutions=100`, `proposed=0` и
`remaining_proposals=100`. После начала поиска журнал не создают заново и не
обнуляют. Его физическое хранилище должно удовлетворять требованиям
`common/search-history.md`, включая локальную файловую систему для SQLite.

Сначала сохрани код, `build.py`, промпты, `solution.json` и digests внешних
зависимостей в каталоге кандидата. Затем зарегистрируй его через
`evaluator.search propose` по общему протоколу. Укажи фактические расходы создания
кода; неизвестную часть токенов пометь `--tokens-incomplete`. Эти расходы относятся
к исследованию, а расходы исполнения `build.py` доверенный сервис измерит отдельно.
Каждая версия, в том числе со сломанной сборкой, расходует одно место из 100.

Build CLI восстанавливает именно зарегистрированный снимок. После регистрации
не меняй его файлы, чтобы под тем же ID получить новую сборку. Изменённый рецепт,
параметры или зависимости требуют новой версии с сохранёнными родителями.

## Интерфейс build.py

В изолированном запуске `/candidate` и `/assets` доступны только для чтения;
`/output` — отдельный каталог результата с записью. Скрипт получает через stdin
JSON со следующими полями:

```json
{"assets_dir":"/assets","candidate_dir":"/candidate","workspace_dir":"/tmp/arena-workspace","output_dir":"/output","parameters":{},"model":"deepseek-ai/DeepSeek-V4-Flash-0731","model_base_url":"временный gateway URL","model_request_timeout":130410}
```

Поля `input` и `reference` отсутствуют. Скрипт пишет готовое представление в
`output_dir` и возвращает один JSON-объект; сообщения для диагностики направляет
в stderr. Заявленные скриптом время или токены не считаются измерением. Таймаут
сборки задаёт `prepare_timeout`, в кампании — 48 часов. Gateway выполняет до пяти
технических повторов после первой попытки с прежними входом и настройками;
дополнительный цикл повторов клиента не нужен. URL содержит секрет допуска и
не записывается в файлы, ошибки, argv, переменные окружения или трейсы.

После успешной сборки сервис сам публикует `/output` неизменяемым и связывает
результат с digest кандидата. При оценке этот результат появляется readonly
в `/assets/prepared`. Не добавляй его неизвестный заранее digest в собственный
`solution.json` после регистрации: соответствие устанавливает доверенная квитанция.
Исходная KB остаётся отдельно в `/assets/kb`; цитаты продолжают ссылаться на
исходный `/kb/norm/<origin_id>.md`.

## Запуск и получение квитанции

Команды выполняются исследователем после отдельного старта поиска и регистрации
кандидата. Они не выполняются при подготовке арены на настоящей KB.

```bash
python -m evaluator.build submit \
  --journal cases/sc71/campaigns/sc71-first-20261019/search.sqlite3 \
  --candidate candidate-001 \
  --url http://train-evaluator:8080 \
  --token-file /run/arena/train-token \
  --output cases/sc71/campaigns/sc71-first-20261019/candidate-001-build.json
```

Ответ содержит `candidate_digest` и состояние `RUNNING`, `FINISHED` или `FAILED`.
Сохрани digest и результат; для чтения состояния используй его же:

```bash
python -m evaluator.build status \
  --digest '<candidate_digest из submit>' \
  --url http://train-evaluator:8080 \
  --token-file /run/arena/train-token \
  --output cases/sc71/campaigns/sc71-first-20261019/candidate-001-build.json
```

API: `POST /v1/builds` с `{"candidate": <Candidate>}` и
`GET /v1/builds/<candidate_digest>`. Авторизация та же, что у train API. Первый
принятый запуск возвращает HTTP 202; повторная отправка того же digest возвращает
существующую квитанцию и не запускает сборку заново. Это относится и к `FAILED`:
автоматической пересборки после ошибки нет. Ошибка и фактические затраты сохраняются.

Следуй `common/long-runs.md`: оставляй выполнение независимым от чата, сохраняй
состояние и ожидай завершения без частого модельного опроса. Build и проверки
используют общие слоты исполнения. При занятой вместимости API возвращает 503
и `Retry-After`; это не новая версия кандидата. После команды остановки новые
сборки не отправляют, результаты уже выполняющихся можно читать.

Оценку train/public/private разрешено отправлять только после `FINISHED` для
того же digest. Эти сервисы не строят представление автоматически. Кандидат с
`build.py` без готовой корректной квитанции получает явный отказ, а не нулевые
расходы. Отдельный build-run не получает quality-score и не создаёт второе
предложение решения. Его успех доказывает исполнение подготовки, а не качество ответа.

## Повторное использование и учёт

Зависимые материалы перечисляются в `parameters.asset_digests`:

```json
{"harness":"hermes","parameters":{"mode":"retrieval","asset_digests":["<digest родительского представления>"]}}
```

Они доступны readonly в `/assets/derived/<digest>`. Если digest известен сервису
как результат измеренной сборки, у нового кандидата обязателен собственный
`build.py`, даже когда достаточно использовать материал без изменений. Такой
скрипт может вернуть пустой JSON или записать небольшой manifest; копировать
родительский индекс в `/output` не нужно. Runner сохраняет доступ к выбранному
материалу по прежнему пути. Сервис автоматически связывает квитанции зависимостей
и учитывает их транзитивно. Кандидат без собственного `build.py`, пытающийся взять
известный измеренный результат через `asset_digests`, отклоняется.

Доверенная квитанция фиксирует digest кандидата, исходной KB, среды и результата,
собственные ресурсы сборки, уникальные квитанции зависимостей, состояние и трейсы.
Собственное время измеряет внешний процесс, токены — gateway, включая технические
повторы и доступные расходы неудачных попыток. Неизвестный usage помечается
неполным и не подменяется полным нулём.

Для каждого самостоятельного сравнения применяется одна схема:

```text
solver_resources = сумма ресурсов всех примеров
                 + собственные ресурсы сборки кандидата
                 + ресурсы уникальных квитанций всех зависимостей
```

Общая подготовка добавляется ровно один раз на целую оценку кандидата: на выбранную
train-подвыборку, весь public или весь private. Она не добавляется к каждому
примеру и не размазывается по вопросам. Одна зависимость, доступная несколькими
путями, учитывается один раз. Общий индекс двух разных кандидатов учитывается в
стоимости каждого из них; стоимость прежних проверок родительского кандидата
в расчёт не входит.

Физический результат сборки переиспользуется между split; сохранённая стоимость
подготовки снова включается в каждое независимое сравнение как стоимость развёртывания
этого метода. Кешированный итог уже включает подготовку и возвращается без повторного
сложения. Доверенные записи разделяют `preparation`, ответы и судейство; итоговые
`solver_tokens`, `solver_seconds` и признаки неполноты включают подготовку и
используются правилом разрешения равенства. Затраты судьи остаются отдельно.
Неудачные сборки сохраняются в истории подготовки и MLflow, а не превращаются в
нулевой score или бесплатную попытку.

## Публикация весов и зависимостей

Исследователь размещает завершённые файлы в `/workspace/staging`, передаёт train API
относительный путь, а сервис копирует их в отдельное неизменяемое хранилище.
Во время публикации программы из staging не исполняются.

```bash
python -m evaluator.assets publish \
  --url http://train-evaluator:8080 \
  --token-file /run/arena/train-token \
  --path models/embedding-v1 \
  --timeout 86400
```

Это `POST /v1/assets` с `{"path":"models/embedding-v1"}`. Ответ содержит `digest`,
`size`, `files` и `asset_path=/assets/derived/<digest>`. HTTP-клиент передаёт только
путь, не содержимое. Кандидат закрепляет digest в `parameters.asset_digests`.
Повторная публикация тех же байтов, путей и executable-битов возвращает тот же digest;
переименование staging-каталога его не меняет. Повторная публикация уже измеренного
представления не снимает его привязку к квитанции и не обнуляет стоимость.

## Операторское хранилище и целостность

Единая настройка квитанций — `ARENA_BUILD_DIR`; поле конфигурации и runner —
`build_dir`. Отпечаток исходной KB передаётся через нейтральную общую настройку `ARENA_INPUT_ASSETS_DIGEST` (`input_assets_digest` в квитанции версии 2). Настройка `ARENA_BUILD_DIR` указывает на операторский каталог с `configuration.json`,
`receipts/<candidate_digest>.json`, `bindings/<output_digest>.json` и
`jobs/<candidate_digest>/`. Train, public и private используют один набор квитанций
и одинаковую замороженную среду. Это не `output_dir` скрипта: последний обозначает
только writable mount `/output` внутри отдельной сборки.

Обычный publisher использует `ARENA_ASSET_STAGING_DIR` и `ARENA_ASSET_STORE_DIR`.
Исследователь пишет staging и читает опубликованные материалы; оператор владеет
хранилищем, квитанциями и родительскими каталогами. Исследователь не получает
Docker socket, права оператора или возможность заменить эти каталоги.

Одна публикация ограничена 64 GiB скопированных байтов, 100 000 элементов дерева,
64 компонентами относительного пути и 64 MiB manifest. Длина пути — до 4096 символов.
Это предел одной операции, не обещание свободного диска. Для публикации временно
нужен ещё один полный экземпляр результата.

Разрешены обычные файлы и каталоги. Symlink, FIFO, устройства, абсолютные пути,
`..`, обратная косая черта и подмена пути ссылкой отклоняются. Имя `.arena-asset.json`
зарезервировано. Изменение открытого файла или каталога во время копирования
вызывает отказ. Manifest содержит пути, типы, размеры, SHA256 и executable-биты;
его канонические байты определяют digest каталога. Пустые каталоги учитываются.
Права нормализуются: каталоги и исполняемые файлы `0555`, остальные файлы `0444`.
Изменение staging после публикации не меняет опубликованные байты.

Runner проверяет manifest и квитанцию, доверяя неизменяемому операторскому
хранилищу; он не перечитывает многогигабайтные веса для каждого примера. Квитанция
с иным digest, KB или средой, небезопасным владельцем либо правами записи
отклоняется. Не удаляй использованные материалы и квитанции до окончания кампании
и срока хранения её воспроизводимых результатов. Полные public/private-записи
остаются только в операторском контуре; общий MLflow получает train и разрешённый
public-score.
