# SC-71: GPU6

Этот каталог содержит базовую конфигурацию SC-71 для GPU6. По команде пользователя от 24.10.2026 готовится отдельная установка `sc71-second-20261024`: [условия](../../campaigns/sc71-second-20261024/campaign.md), [отчёт подготовки](../../campaigns/sc71-second-20261024/preparation.md), [конкретное развёртывание](../../campaigns/sc71-second-20261024/deploy/README.md). В нём фиксируются собственные Compose-конфигурация, сети, порты, volumes, образы и launcher. Готовность новой установки здесь не заявляется; старые результаты проверок на неё не переносятся.

Корень новой установки — `/cephfs/home/malyshev_sa/arena-sc71-second-20261024`. Прежняя установка `/cephfs/home/malyshev_sa/arena-sc71-first-20261019` использует сохранённую серверную копию с `deploy/sc71/`; её release и состояние не перезаписываются новым пакетом. [Исторические свидетельства](../../../../archive/cases/sc71/campaigns/sc71-first-20261019/evidence/README.md) относятся только к первой установке.

В каждой установке `release` содержит проверенный код. `operator`, `secrets`, `logs` и `build` не передаются исследователю. Исследователь получает только очищенный `workspace`, разрешённые `assets` и `research-access` с submit-токенами и отдельным доступом к модели. Оператор использует конкретную конфигурацию выбранной кампании, а не значения первой кампании по умолчанию из базового шаблона.

Поиск запускается отдельной командой пользователя после завершения подготовки. Проверенная команда и имя постоянного исследовательского контейнера записываются в отчёте этой кампании. Повторный запуск без разбора её предыдущего состояния отклоняется. Остановить новые предложения следует инструкцией оркестратору, сохранив уже начатые оценки; принудительное удаление контейнеров для штатной остановки не используется.

## Сервисы

| Доступ исследователя | Назначение |
| --- | --- |
| `http://train-evaluator:8080` | Полные измерения train |
| `http://public-evaluator:8080` | Общий score public |
| `http://private-evaluator:8080` | Отправка финалистов и статус |
| `http://shared-tracking:5000` | Только train и допустимые public-score |
| `http://researcher-gateway:8081` | Зафиксированная внутренняя модель; нужен scoped URL |
| `http://internet-proxy:3128` | Интернет для исследователей, с запретом внутренней адресации |

Имена сервисов в таблице относятся к интерфейсу внутри выбранного окружения; фактические сети и привязки портов задаёт его конфигурация. Submit-токены доступны в `/run/arena/{train,public,private}-token`. Ключ LiteLLM исследователь и решатель не получают. В базовом шаблоне операторские API привязаны к loopback GPU6 на `18730`, `18731`, `18732`; отдельная установка выбирает свои незанятые порты и фиксирует их в отчёте. MLflow с полными закрытыми результатами остаётся на `5050`; отдельное чистое исследовательское хранилище — на `5052`. Название эксперимента не используется как граница доступа.

## Изоляция

В базовом шаблоне `sc71-researchers` и `sc71-workers` — внутренние Docker-сети. Новая отдельная установка получает собственные имена сетей и подсети; их правила проверяются из её контейнеров. Исследователь не имеет Docker socket, SSH-ключей, закрытых данных, операторского окружения или доступа к сервисам хоста. Одноразовый решатель имеет только доступ к `model-gateway:8081`, текущий вопрос и разрешённые assets. Произвольный интернет решателю не выдаётся.

На GPU6 используется `iptables-legacy`; модуль `br_netfilter` включён для фильтрации трафика внутри мостов. `firewall.sh` меняет только выделенные цепочки и добавляет переходы из INPUT и DOCKER-USER. Трафик из подсетей арены разрешён только к перечисленным API; блокируются другие контейнеры, сервисы хоста и соседние workers. IPv6 у сетей должен быть отключён, `net.bridge.bridge-nf-call-iptables` должен равняться `1`. Запуск повторно устанавливает правила; проверка из реальных контейнеров является частью подготовки. Существующие рабочие нагрузки не останавливаются.

Модели embeddings/reranking исследователи могут выбирать после проверки требований. Веса загружаются исследователем в разрешённые материалы и замораживаются перед оценкой. GPU не назначается автоматически: фактическую занятость узла, модели карт и доступную память проверяют до назначения ресурсов и фиксируют в отчёте подготовки. Индексы, SQLite, деревья, README и любые представления KB строятся самим кандидатом и входят в измерения решения.

Для Hermes фиксируются Git-ревизия и версия образа. Профиль с `max_concurrent_children=30`, `oneshot_max_children=30`, глубиной 3, `reasoning_effort=max`, длинными таймаутами и пятью повторами общий для внешнего и внутренних Hermes. Фактические версии, проверки и готовность фиксируются в отчёте выбранной кампании; для новой установки это `cases/sc71/campaigns/sc71-second-20261024/preparation.md`.

Для `sc71-second-20261024` все worktree используют журнал `/workspace/cases/sc71/campaigns/sc71-second-20261024/search.sqlite3` и общую папку `/workspace/cases/sc71/campaigns/sc71-second-20261024`. Физически журнал и рабочие записи размещаются в отдельном Docker volume на локальном диске GPU6; его имя и mount фиксируются в конкретном развёртывании и отчёте. SQLite не хранится на CephFS. Инициализация нового журнала задаёт лимит 100 решений и ноль предложений; прежний журнал не копируется и не сбрасывается.

Перед новым развёртыванием private-сервис получает этот volume только для чтения в `/search`, явный режим `ARENA_SEARCH_MODE=campaign`, ожидаемый лимит предложенных решений `ARENA_SEARCH_MAX_SOLUTIONS=100` и отдельный операторский каталог `operator/search`. До первого хода исследователя и при каждом возобновлении обязателен авторизованный `GET http://private-evaluator:8080/v1/search-readiness`: защита включена, `evaluation_enabled=true`, журнал читается, лимит равен 100, `finalists`, `output_count` и `release_id` совпадают с зафиксированными условиями. Дата, команда и ответ без токена входят в свидетельства готовности; `/healthz` этого не заменяет. После отбора и ревью исследователь выполняет `evaluator.search finalize --bundle ...` с единым журналом. Сервис сверяет замороженный пакет, снимки, лимит предложенных решений и отсутствие выполняющихся проверок. При досрочной остановке требуется операторское свидетельство команды человека в `operator/search/stop.json` по [общему контракту](../../../../deploy/README.md); сам исследователь этот каталог не получает. Эти настройки не меняют существующую private-серию. Новую отдельную серию на прежнем split назначает пользователь; оператор фиксирует команду и отдельное состояние, сохраняя прежнюю историю. Агент не создаёт новую серию самостоятельно посредством переименования или сброса данных.

Launcher исследователя получает явные `--journal`, `--private-url`, `--private-token-file`, `--private-finalists`, `--private-output-count` и `--private-release-id`. Для новой установки оператор переносит в `operator/images.env` обязательные `SC71_FINALISTS`, `SC71_OUTPUT_COUNT` и `SC71_PRIVATE_RELEASE_ID` из уже зафиксированных условий: значения совпадают с условиями выбранной кампании. Для назначенной пользователем `sc71-second-20261024` это `10`, `3` и `sc71-second-20261024`; первая серия сохраняет свои значения и состояние. Compose передаёт эти значения одновременно private-сервису как `ARENA_FINALISTS`, `ARENA_OUTPUT_COUNT` и `ARENA_RELEASE_ID` и launcher как ожидаемые K, N и release ID. Одного `operator/evaluator.env` для интерполяции Compose недостаточно; отсутствие переменных отклоняется при разборе конфигурации. Launcher до создания агента проверяет серверную защиту, лимит предложенных решений из журнала и все ожидаемые значения. Конец диалога Hermes при наличии свободных мест до лимита предложенных решений возвращает ему состояние поиска для продолжения. Повторное завершение без прогресса, ошибка инфраструктуры или преждевременно использованный private дают явное незавершённое состояние вместо успешного завершения кампании. Фиксированные модель, runtime и профиль Hermes этим не меняются.

## Явное подключение возможностей

Для отдельной новой установки образ evaluator собирается с `--build-arg ARENA_TRACKING=true`. Общий образ без этого параметра не включает SDK MLflow. Compose явно задаёт оба адреса MLflow и `MODEL_STRICT_SCHEMA_INTEGERS=true`: строгая запись целого числа нужна неизменённой метрике SC-71; общий gateway по умолчанию использует стандартную JSON Schema.

Профиль оценщиков явно включает `ARENA_RUNNER_SUPPORTS_BUILD=true` и `ARENA_RUNNER_SUPPORTS_ASSET_SELECTION=true`. При использовании реестра харнесов запись Hermes также должна содержать `supports_build: true` и `supports_asset_selection: true`. Для исходной KB оператор задаёт `SC71_INPUT_ASSETS_DIGEST`, передаваемый как `ARENA_INPUT_ASSETS_DIGEST`; идентификатор корпуса задаётся до запуска кампании. В общем протоколе это идентификатор разрешённых входных материалов, а KB — смысл именно SC-71.

В новой версии операция подготовки передаётся в верхнем поле `operation="build"`. Хранилище квитанций использует версию 2 и имя `input_assets_digest`. Старые квитанции и состояние работающей кампании не преобразуются на месте. На будущую установку передаются только отдельно подготовленные и проверенные образы, конфигурация реестра, хранилища и сети.

`launch.sh` проверяет `operator/layout-version` со значением `sc71-case-layout-v2` **до любых Docker-команд**. Старого `operator/READY` недостаточно. Маркер создаётся при подготовке только после отдельного развёртывания, проверки нового протокола, образов, сети, прав, метрики и сервисов. Наличие старых исторических JSON не является основанием создать маркер. Решение пользователя о новой отдельной private-серии и её проверенная готовность фиксируются раздельно: наличие команды не подменяет техническую приёмку, а старый маркер не подтверждает новую установку.

Исходная кампания сохраняет `/workspace/runs/sc71-first-20261019`, прежний протокол и свой `sc71-campaign-runtime`. Подготовка второй кампании не меняет этот mount и не переносит его содержимое в новый журнал.
