# SC-71: трейсы и доступ

Эта конфигурация перенесена локально. Описанные ниже серверы и проверки относятся к исходному развёртыванию кампании; новая структура на GPU6 не установлена. Не применять её к работающей кампании.

Оператор смотрит все train/public/private-трейсы через существующий MLflow `gpu6:5050`. Его контейнер `deus-ex-mlflow-tracking-1`, данные и порт сохранены без перезапуска. Исторические эксперименты при подготовке не читались.

Исследователь получает отдельный чистый MLflow `gpu6:5052`: train и только общий public-score. У него отдельные backend/artifact volumes. Private в этот сервис не экспортируется. Разделение обеспечивают разные серверы, Docker-сети и проверенный firewall, а не имена экспериментов. Оба хостовых порта привязаны к loopback; оператор может открыть интерфейсы через разрешённый SSH-туннель:

```bash
ssh -L 5050:127.0.0.1:5050 -L 5052:127.0.0.1:5052 gpu6
```

Внутри доверенных оценщиков конфигурация:

```text
MLFLOW_TRACKING_URI=http://shared-tracking:5000
ARENA_OPERATOR_MLFLOW_TRACKING_URI=http://operator-tracking:5000
```

Первый адрес разрешён исследовательской сети. Второй существует только в `sc71-operator-tracking`; эту сеть получают доверенные оценщики. Прокси `operator-tracking` передаёт фиксированный Host существующему серверу, не публикует порт и не ведёт access log. Новая сеть присоединена к старому контейнеру с alias `operator-source`; сам сервер не изменён. В этой установке доступ контролируется сетью. У общего и операторского сервера нет общих volumes. Передача операторских сетей, Docker socket или SSH исследователю разрушает эту границу.

## Экспорт

Клиент MLflow фиксируется на `3.16.0`, как сервер. `evaluator.tracking` импортирует SDK только при экспорте; отсутствие SDK и сетевые ошибки создают `tracking_pending`, не повторяют решение. Запись источника не изменяется. Для train доверенный сервис экспортирует один завершённый record в обе очереди; public — полный record оператору и очищенный aggregate в общий сервис; private — только оператору.

```python
export_record(record_path, queue_dir / "operator", operator=True)
export_record(record_path, queue_dir / "shared")
```

Второй вызов запрещён для private. Record содержит `split`, `params` с `case_id`, `campaign_id`, `candidate_id`, `status: FINISHED|FAILED`, `metrics` и исходные времена `start_time_ns`/`end_time_ns`. В `calls` сохраняются `name`, `inputs`, `outputs`, `attributes`, `span_type`, времена и `status: OK|ERROR`. Необязательные `span_id`/`parent_id` задают дерево; дубликаты, неизвестные родители и циклы отклоняются. `LLM`, `TOOL`, `CHAIN` отображаются как отдельные типы spans. Метаданные критерия, номера голоса, роли и примера сохраняются в `attributes`.

Gateway сохраняет фактические попытки в `MODEL_TRACE_DIR/<run_uuid>/<call_uuid>.json`. Оценщик читает их через `read_calls` и связывает с ресурсами решателя/судьи. Закрытый trace volume не монтируется исследователям и runner-контейнерам. Все файлы создаются с правами `0600`, каталоги `0700`; запись атомарная с fsync. Перед сохранением скрываются известные ключи, Authorization, секретный сегмент scoped URL и секреты gateway, включая экранированные формы. Неизвестный usage остаётся неизвестным.

Отдельные очереди можно повторять независимо:

```bash
python -m evaluator.tracking flush --queue /state/tracking-queue/operator --operator
python -m evaluator.tracking flush --queue /state/tracking-queue/shared
```

Команды запускаются внутри соответствующего доверенного сервиса. Очередь закреплена за URI и режимом доступа; её повтор не запускает кандидата и не расходует лимит решений. Идентификатор неизменяемой записи связывает экспорт с одним MLflow run. Run создаётся сразу с идентификатором экспорта; перед повтором проверяются существующие трейсы. Завершение отмечается после проверки наличия трейса на сервере. Локальный журнал кампании остаётся источником порядка решений.

## Развёртывание и проверка

`compose.yaml` использует заранее созданные сети `sc71-researchers`, `sc71-control`, `sc71-operator-tracking`, два новых volumes `sc71-mlflow-shared-backend` и `sc71-mlflow-shared-artifacts` с владельцем `10001:10001`. MLflow запускается из уже установленного образа, заданного через `SC71_MLFLOW_IMAGE`. Версия Nginx указана в compose.

Синтетическая проверка 19 октября 2026 года создала только искусственные записи подготовки, без модельных запросов. В обоих серверах подтверждены пять spans на запись, включая LLM, TOOL и критерий судьи. Экспорт в обе стороны из одного процесса проверен. Отдельная синтетическая проверка прочитала только созданные ею артефакты: public в общем сервисе содержит лишь score и метаданные, операторские public/private содержат полные записи; private-экспорт в общий сервис отвергается. Переключение SDK между адресами восстанавливает исходные настройки окружения. Исследовательская сеть достигает общего сервиса и не достигает операторских адресов, исторического адреса MLflow и хостовых портов 22/5050; окончательные проверки worker/firewall входят в отчёт развёртывания кампании.

## Внешний исследователь и повтор очередей

Доверенный sidecar запускает `python -m integrations.docker.research_monitor watch --config /run/arena/research-monitor.json`. Он проверяет состояние Docker и повторяет очереди каждые 60 секунд обычным процессом, без модельных вызовов. До запуска поиска отсутствие `active.json` означает `not_started`; монитор не создаёт и не запускает исследователя. Отдельный режим `flush --config ... --watch` только повторяет очереди.

Конфигурация содержит `active_file`, `usage_dir`, `trace_dir`, `state_dir`, `params` с явными `case_id`/`campaign_id` и конфигурацией модели/харнеса, списки `shared_queues` и `operator_queues`. В `active.json` доверенный launcher записывает канонический `run_id` и полный `container_id`, полученный после создания контейнера. Монитор не принимает имя контейнера вместо этой привязки. Активный указатель не заменяется новым запуском до разбирательства с предыдущим; launcher кампании отклоняет повторный запуск при существующем файле.

После выхода контейнера монитор ждёт завершения всех активных запросов gateway. Проверка активности и закрытие учёта выполняются под одной блокировкой. Затем сохраняется неизменяемый `state_dir/records/<run_id>.json` с временами, расходами и полными очищенными модельными трейсами. Он имеет `role=orchestrator`, `candidate_id=orchestrator`, `split=train` и не регистрирует предложенное решение и не расходует место в лимите. Расходы внешнего исследования хранятся в `orchestrator_*`; счётчик трейсов сопоставляется с числом попыток. Повторный проход использует тот же сохранённый record, экспортируя его в общий и операторский серверы.

`progress.json` хранит состояние внешнего запуска, `flush-progress.json` — состояние очередей. Ошибка наблюдения или повреждённая запись очереди не блокирует обработку остальных очередей и записей. Неисправная запись не экспортируется. Отсутствующие данные учёта не заменяются нулями. Монитор не читает журналы кандидатов, не возобновляет поиск и не повторяет ответы.

Sidecar получает Docker socket и поэтому входит в доверенный операторский контур. `active.json`, usage, traces, результаты и конфигурация недоступны для записи исследователю. Для sidecar нужны только адреса MLflow, операторские mounts, сети control/operator-tracking и Docker GID; ключ модели ему не нужен.

Сохранённые результаты разрешённой синтетической приёмки экспортируются отдельно, без повторного выполнения сценария:

```bash
python cases/sc71/acceptance/export_acceptance.py \
  --state /operator/acceptance/state.json \
  --output /operator/acceptance/tracking \
  --scenario retrieval --verify
```

Аналогично выбираются `delegation` и `judge`. Экспортёр принимает только конечные состояния `accepted`, `rejected`, `failed` с признаком `synthetic_only`; уже сохранённые ответы не пересчитывает. Для него выделен experiment кейса `sc71-preparation-acceptance`. Сохраняются фактические расходы и, когда он существует, исходный score судьи; отсутствующие расходы остаются `null`. Проверка сверяет точный артефакт записи, статус run и число трейсов/spans на обоих серверах. Очереди `<output>/shared` и `<output>/operator` включаются в конфигурацию монитора.

Для новой установки оба адреса задаются явно: общего адреса по умолчанию нет. Образ оценщика собирается с `--build-arg ARENA_TRACKING=true`. В новой конфигурации монитора train-очереди находятся в `<train-state>/tracking/shared` и `<train-state>/tracking/operator`; production-конфигурация запущенной кампании остаётся прежней.
