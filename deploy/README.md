# Подготовка контейнерного запуска

Команды предназначены для оператора. Перед исследовательским поиском [агент подготовки](../prompts/prepare.md) готовит кейс, метрику, проверки и описание условий кампании. Оператор проверяет подготовленный код, устанавливает его в закрытом окружении и запускает оценщики. Подготовка репозитория сама не развёртывает сервис и не запускает модели. Сначала прочитайте [границы доступа](../common/isolation.md).

Каталог кампании `<campaign_dir>` задаётся явно; он может находиться в `cases/<case>/campaigns/<campaign>/` или в `runs/<campaign>/`. Конкретные серверные адреса, профили харнеса и сценарии приёмки храните в `cases/<case>/deploy/` и `cases/<case>/acceptance/`. Эта инструкция описывает общий контейнерный контракт.

Общий конфиг операторского MLflow proxy и его контейнерная регрессия находятся в [deploy/mlflow](mlflow/README.md). Подключайте его из Compose установки, чтобы настройки потоковой передачи крупных артефактов не расходились между кейсами.

## От подготовки к запуску поиска

1. Пользователь описывает задачу и желаемую оценку в `cases/<case>/metric/`, указывает допустимые изменения, лимит решений и размер итогового набора, а при непустом private — размеры его входа/выхода. Агент подготовки оформляет кампанию, реализует программную, модельную или смешанную оценку и проверяет её на открытых искусственных примерах. Модельные ответы в таких тестах подставные; реальные модельные эксперименты требуют отдельной задачи и зафиксированного числа решений.
2. Подготовленный каталог содержит `metric.json`, код, рубрики и ресурсы. Выполните его семантические тесты, затем заморозьте пакет. Каталог результата должен быть новым:

   ```bash
   uv run python -m evaluator.prepare freeze \
     --metric cases/my-case/metric --output cases/my-case/campaigns/my-campaign/metric
   uv run python -m evaluator.prepare verify --metric cases/my-case/campaigns/my-campaign/metric
   ```

   `freeze` и `verify` проверяют формат, состав и исполняемость файлов; они не выполняют оценку и не доказывают её качество. Готовые примеры лежат в `cases/template/metric/` и `cases/template/metric-examples/`. Их проверяет `uv run pytest tests/test_metric_examples.py` без моделей.
3. Установите весь пакет, включая `metric.lock.json`, в `/srv/arena/metric`. Установите зависимости команды в доверенный образ evaluator и закрепите образ и зависимости. Одинаковый замороженный пакет и окружение используются на train, public и private. Оператор подключает закрытые JSONL отдельно; в метрике, образе и исследовательской копии их нет. Не передавайте подготовительному агенту закрытые данные для реализации метрики.
4. Настройте окружение, runner, постоянное состояние и доступы по следующим разделам. После сборки проверьте пакет именно в окружении evaluator:

   ```bash
   docker compose --env-file /etc/arena/operator.env --profile private build
   docker compose --env-file /etc/arena/operator.env --profile private run --rm --no-deps \
     evaluator python -m evaluator.prepare verify --metric /private/metric
   ```

   Проведите приёмку в отдельном временном сервисе с собственными state/usage и токеном, искусственными данными и подставной моделью: верные и неверные ответы, программная агрегация, ошибки, учёт ресурсов, границы API и рестарт. Приёмка не расходует допуск настоящего private и не использует его данные.
5. Запустите нужные public/private-сервисы и зафиксируйте готовность в `<campaign_dir>/preparation.md`. В записи нужны версии пакета и окружения, пройденные проверки, условия кампании и доступные исследователю URL. Для непустого private обязателен успешный ответ авторизованного `GET /v1/search-readiness` с включённой защитой и совпадающими условиями по разделу ниже. `/healthz` подтверждает только живой процесс, не корректность метрики, доступность модели или защиту private. Любой раздел может быть пустым: его сервис и оценивание не требуются, для пустого private также не выполняются readiness и отправка. Готовность всех нужных оценщиков проверяется до начала поиска.
6. Передайте исследователю [стартовый промпт](../prompts/start.md), подготовленный кейс, открытый train и необходимые submit-доступы. Метрика и её окружение заморожены: не заменяйте пакет, модель, зависимости или образ в работающей кампании. Если обнаружилась ошибка измерителя, остановите кампанию и разберите её с оператором; переименование и удаление состояния не дают новой private-попытки.

## Данные и права

Исследовательский контейнер `researcher` с профилем `train` получает разрешённый train и метаданные кампании. Public и private оцениваются на доверенном узле: для public исследователь получает только score, для private — только статус, включая завершённый финал. Результаты private доступны оператору. Исследователь не получает операторский SSH, Docker daemon, закрытые каталоги или журналы модели.

Копируйте `deploy/operator.env.example` в `/etc/arena/operator.env` вне checkout. Env содержит настройки и пути, ключи хранятся отдельно. Не передавайте операторский env исследовательскому контейнеру. Закрытые данные не должны попадать в Docker build context и Git.

| Путь по умолчанию | Содержимое и права |
| --- | --- |
| `/srv/arena/train` | Чистая исследовательская копия, разрешённый train, результаты; UID 10001 может писать |
| `/srv/arena/search` | Канонический журнал кампании на локальном диске; исследователь пишет, evaluator читает весь каталог через `/search` |
| `/srv/arena/search-control` | Операторские свидетельства остановки; исследователь не получает каталог, evaluator читает через `/search-control` |
| `/srv/arena/private/dataset.jsonl` | Закрытый JSONL: `id`, `input`, необязательный `reference`; только оператор и evaluator |
| `/srv/arena/metric` | Полный замороженный пакет метрики с `metric.lock.json`; читает UID 10001, read-only |
| `/srv/arena/state` | Постоянный закрытый журнал и результаты; владелец UID 10001, режим 0700 |
| `/srv/arena/usage` | Учёт модельных вызовов решателя и собственных команд метрики; UID 10001, режим 0700, доступ только evaluator и gateway |
| `/srv/arena/assets` | Только разрешённые всем кандидатам материалы; каталоги 0755, файлы 0644, read-only |
| `/srv/arena/secrets/submit-token` | Непустой случайный bearer token API; читает UID 10001 |
| `/srv/arena/secrets/model-api-key` | Ключ внутренней модели, если она используется; не передаётся runner |

Ограничьте проход в закрытые каталоги. Пакет метрики монтируется целиком read-only; входной JSONL и секреты монтируются отдельными файлами с доступом для UID 10001. Для модельного API без авторизации в Compose создайте пустой файл model-api-key. Если решатель и оценка полностью программные, модельный сервер и ключ не нужны: используйте запуск без gateway ниже. Общий Compose всё же создаёт gateway; в таком режиме ему нужен пустой файл ключа, но обращения к модели отсутствуют. Submit token даёт только отправку и чтение разрешённого результата API, без административных операций.

`ARENA_STATE_DIR` и `ARENA_ASSETS_DIR` — абсолютные пути, одинаковые внутри evaluator и на Docker-хосте. Они передаются daemon для mounts; замена container path на `/state` сломает связь. Docker daemon работает на том же узле. Не используйте сетевой Docker context или SSH `DOCKER_HOST` для этого Compose.

`ARENA_USAGE_DIR` нужен модельным решателям и собственным командам метрики с `uses_model: true`, включая агрегацию. Не помещайте его в assets или workspace и не монтируйте в runner. Для каждого решения создаётся отдельный идентификатор учёта; gateway принимает зарегистрированные обращения и сохраняет расход подготовки и повторов. Ресурсы из stdout кандидата не используются. Решение без модели запускается без сети и получает доверенный полный учёт нулевых токенов; его время всё равно измеряется.

Assets — неизменяемый снимок кампании. Оценщик сохраняет путь к нему. Read-only mount не защищает от изменений на хосте. `ARENA_DOCKER_GID` задаётся фактической группой сокета (`stat -c '%g' /var/run/docker.sock`), `ARENA_DOCKER_SOCKET` — его путём. Socket получает только evaluator.

## Конфигурация кампании

| Переменная | Значение |
| --- | --- |
| `ARENA_SPLIT` | `private` или `public`; отдельный сервис и хранилище для каждой закрытой части |
| `ARENA_SEARCH_MODE` | `campaign` для поиска, `standalone` для отдельного оценщика вне кампании; общий Compose по умолчанию включает `campaign` |
| `ARENA_SEARCH_DIR` | Каталог канонического журнала на хосте; Compose монтирует его в `/search` |
| `ARENA_SEARCH_JOURNAL` | Путь базы внутри evaluator и исследователя, по умолчанию `/search/search.sqlite3` |
| `ARENA_SEARCH_MAX_SOLUTIONS` | Зафиксированный положительный лимит предложений кампании; число `100` в env-примере заменяется её условием |
| `ARENA_SEARCH_CONTROL_DIR` | Операторский каталог на хосте, монтируемый в `/search-control` только evaluator |
| `ARENA_SEARCH_STOP_PATH` | Путь операторского свидетельства остановки внутри evaluator, по умолчанию `/search-control/stop.json` |
| `ARENA_FINALISTS` | Точное положительное число кандидатов в единственном private-пакете, без предела пять |
| `ARENA_OUTPUT_COUNT` | Точное число лучших решений private, от 1 до `ARENA_FINALISTS` |
| `ARENA_USES_MODEL` | Использует ли харнес по умолчанию модель: `true` или `false` |
| `ARENA_RUNNER_IMAGE` | Образ харнеса по умолчанию, например `arena-runner:local` |
| `ARENA_HARNESSES` | JSON-реестр дополнительных доверенных харнесов |
| `ARENA_RUNNER_SUPPORTS_BUILD` | Поддержка измеряемой подготовки харнесом по умолчанию, `false` по умолчанию |
| `ARENA_RUNNER_SUPPORTS_ASSET_SELECTION` | Выбор опубликованных материалов этим харнесом, `false` по умолчанию |
| `ARENA_PARAMETERS` | Фиксированные параметры запросов модели; не параметры эволюции харнеса |
| `ARENA_MAX_BODY_BYTES` | Транспортный предел размера пакета; при больших пакетах настраивается отдельно от числа решений |
| `ARENA_RELEASE_ID` | Идентификатор замороженных условий; смена ID не открывает новую private-попытку |

Модель и параметры её запросов фиксируются до кампании и совпадают у решателя и LLM-судьи. Они не требуются, если ни решение, ни метрика не используют модель. Код обычной программы может оцениваться LLM-судьёй, а модельное решение — вычисляемой метрикой.

`ARENA_METRIC_PATH` указывает на каталог замороженного пакета. Compose монтирует его в `/private/metric` и передаёт этот путь evaluator. Внутри `metric.json` поле `kind` выбирает встроенный модельный профиль или операторскую команду, `direction` — `maximize` или `minimize`; необязательная `aggregation` задаёт собственный итоговый расчёт по набору. Для команды можно указать переносимый `argv`, например `["python", "score.py"]`. Загрузчик находит интерпретатор в окружении evaluator и разрешает локальные пути пакета. `metric.lock.json` фиксирует состав и исполняемость файлов пакета. Установленные внешние зависимости закрепляются образом и lock-файлами окружения.

Команда может быть полностью программной (`uses_model: false`) либо обращаться к модели (`uses_model: true`). Модельной команде арена выдаёт ограниченный gateway URL, имя зафиксированной модели и таймаут; ключ upstream не передаётся. Та же возможность есть у команды агрегации. Любая схема судейства реализуется внутри подготовленной команды; встроенный `kind: llm` — лишь готовый профиль с настраиваемым `votes`. Исполняемая метрика является доверенным операторским кодом, а не кандидатским плагином в песочнице. Формат описан в [правилах оценки](../common/public-evaluation.md).

Старый `ARENA_METRIC_PATH=/srv/arena/private/metric.json` также допустим: Compose смонтирует этот файл по `/private/metric`, а загрузчик прочитает прежний JSON с закреплёнными абсолютными командами. Для новых кампаний используйте целый пакет. Не переводите активную кампанию на новый формат и не обновляйте runtime посреди серии; сохранённая конфигурация защищена от изменений.

Статическая конфигурация модельного судьи проверяется при создании приложения, до допуска private: endpoint, запрещённые параметры запроса и JSON без NaN. Каждая проверка получает отдельный счётчик обращений судьи. Программная метрика не требует модельного клиента. Собственная модельная команда также проверяет настройки до допуска, а её обращения и агрегация учитываются отдельно от решателя через gateway. Ошибки команды метрики и агрегации сохраняют в закрытых `details` и `record.json` код завершения, признак таймаута и ограниченные stdout/stderr. Эти сведения доступны только оператору; API не раскрывает их.

Промпт кампании отдельно задаёт допустимые изменения компонентов решения, выбор среди зарегистрированных харнесов и их параметры. Любой из этих компонентов может быть фиксированным или переменной эволюции; совместный поиск разрешён, если предусмотрен условиями кампании. Реестр замораживается до запуска. Пример его формы:

```json
{"program":{"image":"arena-program:local","uses_model":false,"network":"none"},"agent":{"image":"arena-agent:local","uses_model":true,"network":"arena-runners"}}
```

Для каждого зарегистрированного харнеса флаги `supports_build` и `supports_asset_selection` также задаются явно и по умолчанию равны `false`; именованные профили не наследуют эти флаги харнеса по умолчанию. При выключенных возможностях обычный `build.py` и параметр `asset_digests` сохраняют смысл, заданный адаптером; наличие файла или поля не подключает инфраструктуру автоматически.

`solution.json` кандидата выбирает зарегистрированный ID и передаёт параметры адаптеру; произвольные образы и mounts не принимаются. Один и тот же пакет проверяется в одинаковой конфигурации на всех split. Протокол и комплектный runner описаны в [контракте](../common/runner-contract.md) и [runner/README.md](../runner/README.md).

Соберите операторский runner отдельно и укажите его тег в `ARENA_RUNNER_IMAGE`:

```bash
ARENA_RUNNER_IMAGE=arena-runner:local
```

Dockerfile устанавливает зависимости из `uv.lock` через `uv sync --frozen`; теги базовых образов в шаблоне остаются выбором оператора. MLflow SDK устанавливается только при `docker build --build-arg ARENA_TRACKING=true ...`; по умолчанию этот extra выключен.

У отдельного кандидата нет фиксированного предела суммарного размера файлов или их количества. При отправке клиент применяет настраиваемый предел всего пакета: `--max-bundle-bytes` или `ARENA_MAX_BUNDLE_BYTES` (по умолчанию 72 MiB). Согласуйте его с `ARENA_MAX_BODY_BYTES` сервиса и reverse proxy с учётом размера кандидатов и их числа. Эти транспортные пределы не применяются к локальным `pack` и `finalize`.

Лимит поиска — число предложенных решений в [журнале кампании](../common/search-history.md). Env оценщика не устанавливает лимит токенов поиска. Неудачные решения входят в счётчик и сохраняются. Команда остановки прекращает новые решения и проверки, дожидается начатых и переводит кампанию к отбору по имеющимся результатам.

Для private-сервиса поисковой кампании с непустым private задайте `ARENA_SEARCH_MODE=campaign`, `ARENA_SEARCH_JOURNAL` и `ARENA_SEARCH_MAX_SOLUTIONS`. При отсутствии журнала или лимита этот режим не запускается; неподключённый, повреждённый или несовместимый журнал не позволяет подтвердить готовность или принять private. Корневой Compose уже передаёт эти переменные и монтирует весь каталог журнала read-only в evaluator. Исследователь получает тот же каталог на запись через `/search`; все worktree используют эту единственную базу. До проверки готовности создайте каталог и инициализируйте журнал по [контракту истории](../common/search-history.md) с лимитом кампании. Подготовка пустого журнала не запускает поиск и не занимает места в лимите предложенных решений. При возобновлении используйте прежнюю базу.

Каталог журнала должен находиться на локальном диске и содержать служебные файлы SQLite. Не используйте копию базы, сетевую файловую систему или `immutable=1`. Заранее создайте операторский каталог `ARENA_SEARCH_CONTROL_DIR`; он монтируется только evaluator и не должен находиться внутри исследовательского workspace или каталога журнала. Файл остановки может отсутствовать. Compose не создаёт отсутствующие каталоги автоматически.

Проверьте защиту private авторизованным `GET /v1/search-readiness`, используя тот же адрес и submit-доступ, которые получит исследователь. Ответ должен иметь `mode="campaign"`, `gate_enabled=true`, `journal_ready=true`, `evaluation_enabled=true`; `max_solutions`, `finalists`, `output_count` и `release_id` должны совпадать с условиями кампании. Сохраните команду, дату, URL и ответ без токена в `<campaign_dir>/preparation.md`. Проверка читает только конфигурацию и журнал, не расходует private-попытку и не раскрывает закрытые результаты. Неверный маршрут, HTTP-ошибка, отключённая защита или несовпадение условий означают незавершённую подготовку. Перед каждым стартом или возобновлением поиска повторите эту проверку; старой записи готовности недостаточно.

Команда ниже проверяет эти поля и завершается с ошибкой при несовпадении. Замените адрес, путь токена, числа и release ID условиями кампании:

```bash
uv run python -m evaluator.client search-readiness \
  --url http://127.0.0.1:8080 --token-file /srv/arena/secrets/submit-token \
  --require-campaign --max-solutions 100 --finalists 5 --output-count 1 \
  --release-id replace-with-frozen-release-id
```

Самостоятельный evaluator вне поисковой кампании явно запускается с `ARENA_SEARCH_MODE=standalone` и пустыми `ARENA_SEARCH_JOURNAL`, `ARENA_SEARCH_MAX_SOLUTIONS`, `ARENA_SEARCH_STOP_PATH`. Смешивание `standalone` с настройками журнала отклоняется. В общем Compose каталоги `/search` и `/search-control` остаются mounts и должны существовать, но база и свидетельство остановки не требуются. Для самостоятельного запуска без Compose эти mounts не нужны. Ответ readiness в таком режиме не является допуском к поисковой кампании.

Перед submit исследователь выполняет `evaluator.search --journal <path> finalize --bundle <path>` по [контракту журнала](../common/search-history.md). Сервис сверяет законченный поиск и точный пакет перед первым private-допуском. Отказ до принятия не расходует private-попытку: предварительный выбор можно исправить через `finalize --replace` из уже зарегистрированных снимков, без новых предложений и проверок. Единственный необратимо принятый набор хранится в закрытом `record.json`; его последующая ошибка исполнения не возвращает допуск. Public и повторная доставка уже принятого private-пакета сохраняют прежнее поведение. `/healthz` не подтверждает готовность поиска к финализации.

Для досрочной команды человека оператор дополнительно публикует JSON по `ARENA_SEARCH_STOP_PATH`. Этот файл и родительский каталог не должны быть доступны исследователю на запись; путь можно настроить заранее, файл не требуется при достижении лимита предложенных решений. Значения `batch_digest`, `stopped_at` и `reason` должны совпадать с замороженным пакетом и журналом, `source_ref` указывает на конкретную команду человека:

```json
{
  "batch_digest": "<digest итогового пакета>",
  "stopped_at": "<campaign.stopped_at из журнала>",
  "reason": "<campaign.stop_reason из журнала>",
  "source_ref": "<ссылка или ID сообщения человека>"
}
```

Не создавайте это свидетельство по самостоятельному решению агента завершить поиск. `stop --reason` и `finalize` не являются операторским подтверждением. При изменении времени остановки или пакета старый файл не подходит. Запись допуска с использованными условиями сохраняется в закрытом `record.json`; API продолжает возвращать только статус.

## Длительная работа

Интервалы задаются в секундах: конечные положительные значения, для задержки повторов допустим ноль. Модельный запрос имеет первую попытку и до пяти повторов при ошибке с теми же входом и настройками. Валидный низкий результат не повторяется. Паузы по умолчанию — 30, 90, 240, 540 и 900 секунд, суммарно 30 минут без учёта длительности самих запросов.

| Переменная | По умолчанию | Что ограничивает |
| --- | --- | --- |
| `ARENA_MODEL_TIMEOUT` | `21600`, 6 часов | Одну попытку решателя или судьи |
| `ARENA_RETRY_DELAY` | `30` | Базовую задержку повтора; множители 1, 3, 8, 18, 30, каждая пауза не больше 900 секунд |
| `ARENA_PREPARE_TIMEOUT` | `172800`, 48 часов | Подготовку комплектного раннера |
| `ARENA_RUNNER_TIMEOUT` | `604800`, 7 суток | Решение одного примера, включая подготовку и повторы |
| `ARENA_EVALUATOR_TIMEOUT` | `3600`, 1 час | HTTP-запрос клиента, не всю серию |

Комплектный runner ждёт gateway дольше шести попыток и пауз: при этих настройках 131460 секунд. В gateway таймаут ограничивает всю попытку, у судьи — сетевые операции HTTP-клиента. Внешний лимит runner должен покрывать подготовку и все вызовы харнеса. Эти таймауты защищают от зависания и не ограничивают суммарное число токенов или длительность кампании.

Reverse proxy, модельный сервер, очередь и среда агента должны допускать эти длительности. Увеличьте время жизни субагентов и глубину вложенности, если среда это поддерживает. Ожидание описано в [правилах долгих запусков](../common/long-runs.md).

Модельный сервер возвращает достоверный `usage`. Если корректный ответ получен без usage или с некорректным usage, ответ сохраняется без повторного обращения, а расход отмечается неизвестным через `unreported_attempts`. После обрыва без usage расход также неизвестен, а не нулевой. Решатель и судья учитываются раздельно. При равном качестве сравниваются ресурсы решателя по [общему правилу](../common/public-evaluation.md).

## Закрытый сервис с модельным gateway

После настройки env:

```bash
docker compose --env-file /etc/arena/operator.env --profile private config --quiet
docker compose --env-file /etc/arena/operator.env --profile private build
docker compose --env-file /etc/arena/operator.env --profile private up -d
```

Профиль Compose `private` обозначает доверенную инфраструктуру; режим API определяется `ARENA_SPLIT`. Compose публикует evaluator на `127.0.0.1:8080`; gateway порты не публикует. `/healthz` проверяет процесс, а не доступность модели. Для удалённой отправки настройте TLS reverse proxy с подходящими пределами тела и времени запроса либо ограниченный туннель к одному API-порту. Исследователю не выдаётся SSH-ключ оператора.

Сеть worker является `internal`: только gateway и краткоживущие runner. Evaluator подключён к `backend`. Проверьте firewall: worker не должен достигать служб хоста, других Docker-сетей, интернета или модельного upstream в обход gateway. Backend имеет выход только к разрешённому внутреннему API; Compose сам firewall хоста не настраивает.

Для public создайте отдельный env с `ARENA_SPLIT=public`, закрытым public JSONL, отдельными state, usage, токеном, release ID, портом и именем runner-сети. Запускайте его с отдельным `--project-name arena-public`. Явные `network` модельных профилей в `ARENA_HARNESSES` должны указывать на сеть этого сервиса, не соседнего private-развёртывания. Public принимает ровно одного кандидата за запрос, запускает отдельного работника до ответа `202` и отдаёт только score. Независимые запросы выполняются параллельно без очереди в общем пуле; `evaluation_id` из submit передаётся клиенту `status --evaluation-id`. Пустой public или private не требует сервиса. Если сервис запущен с пустым разделом, он отклоняет оценивание до запуска кандидатов и расходования private-допуска; нулевой score и победители не создаются. При непустом private сервис принимает один неизменяемый пакет точного размера и возвращает только статус. Выбранные `ARENA_OUTPUT_COUNT` решения и рейтинг хранятся у оператора.

После исчерпания повторов серия получает `failed`; API продолжает работать. После прерывания процесса активная серия также становится `failed`. Идентичная доставка возвращает сохранённое состояние, не запускает повторно. Автоматического продолжения после рестарта и API retry/reset нет. Оператор разбирает причину в закрытом журнале, не раскрывая частичные результаты.

Не удаляйте private state и не переименовывайте кампанию, чтобы отправить изменённый пакет на тот же holdout. Сохраняйте историю допусков при переносе сервиса. Для первого приёмочного запуска используйте искусственные данные: проверьте изоляцию, учёт ресурсов, идемпотентность, сохранение допуска после рестарта и отсутствие закрытых деталей в API. Тесты репозитория не проверяют сеть конкретного Docker-хоста.

### Ожидание public/private

Для уже отправленной проверки используйте штатный `wait`; он делает только GET-запросы и сохраняет каждый валидный ответ API в обязательный `--output`. Public требует `--evaluation-id` из submit, private читается без него:

```bash
uv run python -m evaluator.client wait \
  --url https://public-evaluator.example --token-file /run/secrets/public-submit \
  --evaluation-id '<evaluation-id>' --output runs/example/public-status.json
uv run python -m evaluator.client wait \
  --url https://private-evaluator.example --token-file /run/secrets/private-submit \
  --output runs/example/private-status.json
```

Ожидание продолжается только при `running`: `complete` завершает команду кодом 0, `failed` — кодом 3, неизвестный статус, неверный ответ или ошибка запроса — кодом 1. `--poll-seconds` задаёт конечный положительный интервал, по умолчанию 60 секунд; `--timeout` ограничивает отдельный HTTP-запрос, общего лимита длительности проверки нет. Коды 1 и 3 обрабатывайте явно, не превращая их в повторную отправку кандидата. Public сохраняет только разрешённый ответ с общим score при успехе, private — только статус; `failed` не подменяется нулевым score. Для train применяется отдельный `evaluator.train` со статусами `RUNNING`, `FINISHED`, `FAILED`.

## Сервис без модели

Когда решатель и метрика не используют LLM, gateway и ключ модели не нужны. На доверенном узле с Docker и установленными зависимостями запустите evaluator с операторскими переменными окружения. В отличие от Compose, процесс читает `ARENA_TOKEN_FILE`, а не переменную пути монтирования `ARENA_SUBMIT_TOKEN_FILE`:

```bash
ARENA_DATASET_PATH=/srv/arena/private/dataset.jsonl \
ARENA_METRIC_PATH=/srv/arena/metric \
ARENA_STATE_DIR=/srv/arena/state \
ARENA_TOKEN_FILE=/srv/arena/secrets/submit-token \
ARENA_RUNNER_IMAGE='arena-runner:local' \
ARENA_RELEASE_ID=replace-with-frozen-release-id \
ARENA_USES_MODEL=false \
ARENA_RUNNER_NETWORK=none \
ARENA_MODEL='' \
ARENA_MODEL_BASE_URL='' \
ARENA_SPLIT=private \
ARENA_SEARCH_MODE=campaign \
ARENA_SEARCH_JOURNAL=/srv/arena/search/search.sqlite3 \
ARENA_SEARCH_MAX_SOLUTIONS=100 \
ARENA_SEARCH_STOP_PATH=/srv/arena/search-control/stop.json \
ARENA_FINALISTS=5 \
ARENA_OUTPUT_COUNT=1 \
uv run python -m evaluator
```

Замените образ и числа на условия кампании, заранее инициализируйте канонический журнал и проверьте `search-readiness` по общей процедуре. Здесь пути журнала и остановки относятся непосредственно к хосту. Для отдельного оценщика вне кампании используйте описанный выше режим `standalone`. Пакет метрики должен быть заморожен и доступен процессу, его внешние зависимости установлены в том же закреплённом окружении. Для длительной службы используйте доступный на узле менеджер процессов. Процесс слушает порт 8080; доступ ограничивает операторская сеть или reverse proxy.

## Исследовательский контейнер

`ARENA_TRAIN_WORKSPACE` содержит чистую копию с разрешённым train, без операторского env, закрытого state, токенов модели или ссылок на закрытые материалы. Простой mount текущего каталога оператора не подходит. Необходимый CLI-харнес оператор добавляет в свой image либо работает из ограниченного чата.

```bash
docker compose --env-file /etc/arena/operator.env --profile train build researcher
docker compose --env-file /etc/arena/operator.env --profile train run --rm researcher
```

Исследователь видит свой workspace, общий журнал `/search` и разрешённую сеть. Один операторский env-файл в командах Compose согласует host paths; сам файл внутрь researcher не передаётся. Доступ к внутренней модели для train настраивается отдельно; закрытый gateway ему недоступен. Модельные вызовы с данными направляются только внутренним моделям; не передавайте данные облачному чату-оркестратору. Ограничение egress задаёт инфраструктура оператора.

В общем Compose `ARENA_MLFLOW_URL` передаётся исследователю как `MLFLOW_TRACKING_URI`. Пустое значение отключает общий экспорт. Закрытый получатель задаётся только доверенному сервису через `ARENA_OPERATOR_MLFLOW_TRACKING_URI`; выбранные получатели проверяет оператор. Адресов по умолчанию нет. Правила экспорта, очередей и разделения доступа описаны в [MLflow](../common/mlflow.md).

## Необязательный train-сервис и подготовка материалов

`uv run python -m evaluator.train serve` запускает общий доверенный измеритель открытого train с теми же runner и метрикой. Кейс задаёт свой JSONL, пакет метрики и зарегистрированные харнесы; сам сервис не зависит от домена кейса. Пустой train допускается для запуска build и publisher, а запрос оценивания пустого набора отклоняется без запуска проверки. Помимо общих настроек оценщика ему нужны `ARENA_CAMPAIGN_ID`, `ARENA_CASE_ID`, `ARENA_DATASET_ID`, `ARENA_CONDITIONS_ID` и собственные state, токен и данные. `ARENA_TRAIN_TRACKING=false` отключает экспорт train; при включённом экспорте используются только явно настроенные URI. Train допускает выбор подвыборки, возвращает результаты и трейсы; закрытый сервис сохраняет прежнюю границу public/private.

Для чтения train-трейсов через MLflow задай `ARENA_TRAIN_TRACKING=true` и общий `MLFLOW_TRACKING_URI` train-сервису, установи ему extra `tracking`. Исследователю передай URI того же общего сервера и доступ к чтению из его сети. В gateway включи `MODEL_TRACE_DIR`, а в train-сервисе укажи `ARENA_TRACE_DIR`: оба пути должны вести к одному доверенному хранилищу вызовов через соответствующие mounts. Иначе модельные запросы через gateway не попадут в train-трейс. Сырые каталоги вызовов и операторский MLflow исследователю не передаются; он читает очищенные train-трейсы через общий сервер.

Эти настройки и mounts задаются в отдельном train-сервисе или Compose override; одного `ARENA_MLFLOW_URL` исследователя недостаточно. Если MLflow используется для train-измерений, до поиска проверь экспорт синтетической train-записи и чтение содержимого её трейса из исследовательской среды по [инструкции MLflow](../common/mlflow.md). Если такой экспорт обязателен для кампании, недоступные train-трейсы означают незавершённую подготовку.

Клиент работает с зарегистрированным снимком из журнала, а не с текущими изменяемыми файлами:

```bash
uv run python -m evaluator.train submit \
  --url https://train-evaluator.example --token-file /run/secrets/train-submit \
  --journal cases/my-case/campaigns/my-campaign/search.sqlite \
  --candidate way-a --measurement way-a-train \
  --dataset train-v1 --conditions conditions-v1 \
  --train-data cases/my-case/dataset/train/dataset.jsonl
uv run python -m evaluator.train status \
  --url https://train-evaluator.example --token-file /run/secrets/train-submit \
  --evaluation-id '<returned-id>'
```

Команда `result` дополнительно принимает `--journal`, `--measurement` и `--output`, сохраняет завершённый результат и связывает его с замером. `--example-id` у `submit` выбирает train-подвыборку. Повторные замеры неизменного кандидата используют уже полученные корректные ответы; отсутствие MLflow не препятствует измерению.

Train-сервис может дополнительно предоставить publisher и build API. Они не включаются общим Compose автоматически: нужен отдельный сервис или Compose override, который передаёт флаги возможностей и пути хранилищ оценщику и монтирует соответствующие каталоги. Одного изменения `operator.env` недостаточно. Оператор задаёт `ARENA_ASSET_STAGING_DIR` для доступного исследователю staging, `ARENA_ASSET_STORE_DIR` для доверенного неизменяемого хранилища, `ARENA_BUILD_DIR` для закрытых квитанций и `ARENA_INPUT_ASSETS_DIGEST` для закреплённых исходных материалов. Runner и eval-сервисы получают это же хранилище через `ARENA_PUBLISHED_ASSETS_DIR` и одинаковые настройки харнеса. Исследователь не получает запись в публикации, квитанции или Docker socket. Общий предел одновременного исполнения задают `ARENA_SLOT_DIR` и `ARENA_EXECUTION_SLOTS`.

```bash
uv run python -m evaluator.assets publish \
  --url https://train-evaluator.example --token-file /run/secrets/train-submit \
  --path allowed-import
uv run python -m evaluator.build submit \
  --url https://train-evaluator.example --token-file /run/secrets/train-submit \
  --journal cases/my-case/campaigns/my-campaign/search.sqlite --candidate way-a
uv run python -m evaluator.build status \
  --url https://train-evaluator.example --token-file /run/secrets/train-submit \
  --digest '<candidate-digest>'
```

`ARENA_BUILD_DIR` обязателен при `supports_asset_selection: true`, даже если разрешены только готовые веса и `supports_build: false`. Это общий доверенный журнал квитанций и связей для данного хранилища публикаций. Пустой каталог вместо существующего журнала не допускается: потеря связей не должна превращать оплачиваемую подготовку в бесплатный импорт. Каталог и файлы журнала принадлежат UID оценщика, не доступны для записи группе или остальным пользователям и не являются символическими ссылками.

Train-сервис создаёт журнал через `BuildStore` при старте с настроенными `ARENA_BUILD_DIR`, `ARENA_PUBLISHED_ASSETS_DIR` и `ARENA_INPUT_ASSETS_DIGEST`. Запустите его до закрытых оценщиков: они проверяют уже созданную конфигурацию. Для нового развёртывания без train-сервиса оператор может выполнить следующую инициализацию в окружении оценщика, с его окончательными переменными `ARENA_*` и UID:

```python
from evaluator.build import BuildStore, run_build
from evaluator.build_receipts import build_environment
from evaluator.execution import make_runner
from evaluator.service import Settings

settings = Settings.from_env()
if (settings.build_dir is None or settings.published_assets_dir is None
        or settings.input_assets_digest is None):
    raise ValueError("Configure receipt storage, published assets and input digest")
runner = make_runner(settings, settings.usage_dir or settings.state_dir / "usage")
BuildStore(
    settings.build_dir, settings.published_assets_dir, settings.input_assets_digest,
    build_environment(runner, settings.parameters),
    lambda candidate, output: run_build(runner, candidate, output),
    dependency_assets=runner.build_asset_digests,
)
```

Конструктор создаёт `configuration.json`, `receipts/`, `jobs/` и `bindings/`; вручную писать конфигурацию не нужно. Сам этот вызов не собирает кандидата, не запускает Docker и не обращается к модели. Отпечаток окружения вычисляется из того же реестра харнесов и параметров, которые будут у оценщиков. Не создавайте другой журнал для прежнего хранилища и не переинициализируйте состояние работающей кампании.

Путь публикации относителен staging; API не принимает произвольный путь хоста. Build требует зарегистрированного кандидата и выбранного харнеса с `supports_build: true`. Операция, mounts, квитанции версии 2 и обязательный учёт зависимостей описаны в [общем контракте](../common/runner-contract.md). Новый формат предназначен для новых развёртываний: не заменяйте квитанции или runtime уже работающей кампании.

Docker-монитор завершения внешнего исследователя вынесен в [необязательную интеграцию](../integrations/docker/README.md): `python -m integrations.docker.research_monitor`. Его конфигурация и доступ к Docker остаются у оператора; конкретная топология не является частью протокола оценки.

## Инструменты и проверка JSON в gateway

Gateway принимает от 1 до 10 000 сообщений в одном запросе; отдельно действует предел тела запроса, по умолчанию 16 MiB.

Gateway допускает клиентские `tools` и `tool_choice`. Оператор может закрепить одно или оба поля в `MODEL_PARAMETERS_JSON`: клиент может опустить закреплённое поле или повторить его точное JSON-значение, но не изменить. Незакреплённые поля выбирает клиент; итоговый набор инструментов и выбор проверяются на совместимость.

Для структурированного ответа оператор задаёт список разрешённых схем через `MODEL_RESPONSE_SCHEMAS_JSON`; `response_schema` клиента должен точно совпадать с одной из них. Поддерживается ограниченное подмножество JSON Schema: типы, свойства, обязательные поля, дополнительные свойства, массивы, границы чисел и длины, `enum`, `const`, `title`, `description` и только шаблон `\S` для непустого текста. `$ref`, `$defs`, комбинаторы и другие регулярные выражения не поддерживаются. Предел схемы — 32768 байт, глубина 16, 2048 узлов; глубина JSON-ответа — 64. Неподдерживаемая схема отклоняется при настройке.

`MODEL_STRICT_SCHEMA_INTEGERS=false` сохраняет стандартную семантику JSON Schema: `1.0` удовлетворяет `integer`. Если зафиксированная метрика требует именно JSON-целые без дробной формы, оператор явно включает `true` в её gateway. Флаг принимает только `true` или `false`. Невалидный ответ проходит прежние технические повторы с тем же запросом; политика проверки фиксируется до кампании.
