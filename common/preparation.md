# Подготовка арены

Подготовка выполняется отдельным запуском по [промпту агента подготовки](../prompts/prepare.md). Пользователь описывает задачу, желаемую оценку и условия кампании; агент превращает их в исполнимую конфигурацию, проверяет её и завершает работу передачей результатов пользователю. Затем пользователь отдельно запускает поиск с готовыми результатами подготовки. Это роли обычных агентов, а не отдельный агентный движок. Подготовка метрики и проверки на синтетических входах не учитываются в числе предложенных решений. Реальное решение, предложенное для поиска, регистрируется по общим правилам.

## Что передать агенту

Положи описание задачи в `cases/<case>/README.md`, описание оценки — в `cases/<case>/metric/`. Достаточно начать с текста: формат ответа, признаки правильности, ошибки, шкала и направление улучшения, необходимые эталоны, правила сведения результатов в один score. При наличии добавь реализацию, проверочные примеры с ожидаемыми оценками и зависимости. Метрика может быть программной, модельной или смешанной; арена не требует LLM-судьи.

Для кампании нужны разрешённые изменения решения и харнеса, фиксированные условия, версии и размеры split, положительный лимит предложений и размер итогового набора. При непустом private отдельно задай точное число финалистов K и итоговых решений N, где N ≤ K. Если используются модели, укажи внутренний endpoint, модель и параметры; модель у решателя и оценщика одна. Зафиксируй, используется ли MLflow и обязателен ли он для кампании; при использовании MLflow для train-измерений исследователь должен уметь читать их трейсы через разрешённый общий сервер. Секреты передаются через операторскую конфигурацию, не через файлы кейса. Закрытые данные и эталоны остаются у оператора.

До подготовки выбери явный `<campaign_dir>`, например `cases/<case>/campaigns/<campaign>` или `runs/<campaign>`. Передай этот путь всем участникам; состояние не ищется автоматически по имени кейса. Данные, журналы исполнения и секреты остаются вне Git, независимо от выбранного каталога.

## Работа агента подготовки

1. Проверь постановку и раздельно зафиксируй известные условия и пробелы. Запиши условия кампании в `<campaign_dir>/campaign.md`. Не заполняй отсутствующие требования выдуманными данными. Поиск решений в этот запуск не входит.
2. Подготовь `metric/metric.json` и нужные программы, инструкции, материалы и зависимости. `kind: command` подходит для собственной оценки и агрегации; `kind: llm` — готовый профиль с эталоном и настраиваемым `votes`. Протокол описан в [правилах оценки](public-evaluation.md).
3. Проверь метрику на открытых или синтетических примерах: правильный и неправильный ответ, граничные случаи, ожидаемый итог набора, сбои. Для программной части используй точные ожидаемые результаты. Для модельной части подставные ответы проверяют обработку и учёт вызовов; качество самого судьи требует отдельного согласованного эксперимента. Не запускай реальные модели без задачи на эксперимент и зафиксированного числа решений.
4. Подготовь совместимый runner, закрепи версии зависимостей и образов, настройки модели, таймауты и хранение результатов. Проверь соединение частей на синтетическом входе без допуска на реальный private. Вызовы модельной метрики проходят через gateway, их usage и время учитываются отдельно от решателя, включая агрегацию и сбои.
5. Заморозь пакет и передай оператору версию, проверки и требования к среде. Оператор проверяет код, устанавливает зависимости и тот же пакет во всех оценщиках. Программа метрики выполняется с правами оценщика; это доверенный код, а не изолированный код кандидата.
6. Если кампания использует MLflow для train-измерений, проверь экспорт синтетической train-записи и чтение полного payload её трейса из исследовательской среды по [правилам трекинга](mlflow.md). Запиши общий URI без секретов и experiment/run/trace ID для повторной проверки. Наличие run или метрик без доступных входов и выходов вызовов недостаточно. При обязательном MLflow отсутствие этого доступа — пробел подготовки; локальные файлы его не заменяют.
7. До запуска поиска инициализируй канонический журнал с зафиксированным лимитом предложений; при возобновлении сохрани прежнюю базу. При непустом private оператор подключает её к private-сервису в режиме `ARENA_SEARCH_MODE=campaign`. Для этого сервиса выполни авторизованный `GET /v1/search-readiness` с исследовательским submit-доступом: обязательны `mode="campaign"`, `gate_enabled=true`, `journal_ready=true`, `evaluation_enabled=true`, совпадение `max_solutions`, `finalists`, `output_count` и `release_id` с условиями. Ошибка или несовпадение означает пробел подготовки; `/healthz` и наличие переменных в env-файле эту проверку не заменяют. Подключение и проверка описаны в [развёртывании](../deploy/README.md).
8. Зафиксируй готовность в `<campaign_dir>/preparation.md`: пути и версии условий, путь и версию замороженного пакета, команды и результаты проверок, версии среды, открытые ограничения, готовность необходимых сервисов и доступные исследователю URL. При непустом private приложи дату, команду и ответ проверки его защиты без токена. При использовании MLflow для train-измерений приложи свидетельство чтения train-трейса. Не записывай секреты и закрытые результаты. Заверши запуск отчётом пользователю с путями к результатам. После готовности пользователь отдельно запускает поиск по [стартовому промпту](../prompts/start.md); автоматического перехода нет.

## Заморозка и установка

```bash
uv run python -m evaluator.prepare freeze \
  --metric cases/my-case/metric \
  --output cases/my-case/campaigns/my-campaign/metric
uv run python -m evaluator.prepare verify --metric cases/my-case/campaigns/my-campaign/metric
```

`freeze` создаёт отдельный пакет с `metric.lock.json`, фиксирующим состав и исполняемость файлов. `verify` проверяет этот состав, исполняемость и формат. Они не запускают смысловые тесты (`semantic_tests_run: false`), не доказывают правильность выбранной метрики и не заменяют её проверки. Замороженный каталог не редактируют; изменение метрики требует новой версии условий до начала поиска. При проверке Python-кода используй `PYTHONDONTWRITEBYTECODE=1`, чтобы не добавлять в пакет `__pycache__`.

Оператор переносит пакет в окружение оценщика и задаёт `ARENA_METRIC_PATH` на его каталог. Сервис загружает пакет при старте; исследователь не загружает код метрики через API и не меняет её вместе с кандидатом. Старый формат пути к готовому `metric.json` с закреплёнными командами также поддерживается. Инструкции установки и разделения учётных записей — в [deploy/README.md](../deploy/README.md).

Перед поиском должны быть готовы runner, учёт ресурсов и измерители непустых разделов. Любой раздел может быть пустым: тогда его оценивание пропускается, а сервис не требуется. При пустом private readiness и отправка на него не выполняются; итоговый выбор сохраняется по условиям кампании и доступным свидетельствам без закрытого ранжирования. Train-сервис можно запустить с пустыми данными ради build и publisher, если эти возможности нужны. Метрика устанавливается в них до оценки; отдельный постоянно работающий процесс для каждой метрики не нужен — оценщик сам вызывает её программу. Проверка готовности не расходует реальный private-допуск. Переустановка сервиса, переименование кампании или новая упаковка прежней метрики не дают нового допуска.

При возобновлении кампании проверь сохранённое состояние и тот же пакет, не запускай подготовку с изменением условий заново. Если обнаружена ошибка измерителя, сохрани её и останови новые сравнения до решения по условиям кампании; исправленные оценки нельзя молча смешивать с прежними.
