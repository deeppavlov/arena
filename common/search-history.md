# Журнал поиска, родословная и кривая эволюции

`evaluator.search` — локальный журнал, которым пользуются оркестратор и исследователи. Он не запускает решатель, не выбирает гипотезы и не заменяет харнес. Общая SQLite-база сериализует регистрацию решений, начало проверок и остановку между процессами на одной машине. Для распределённых работников команды выполняет общий координатор; не размещай базу на сетевой файловой системе.

Создай журнал до первого решения в явно выбранном каталоге кампании: например, `cases/<case>/campaigns/<campaign>/` или `runs/<campaign>/`. SQLite-журнал и локальные результаты исполнения не включаются в Git; исходники кандидатов сохраняются отдельно. Все участники используют один абсолютный путь к журналу; примеры ниже используют `runs/example/`:

```bash
uv run python -m evaluator.search --journal runs/example/search.sqlite init --max-solutions 1000
```

`max_solutions` — обязательное положительное целое число, единственный бюджет поиска. Лимитов токенов и общего времени нет. Расходы всё равно измеряются. Число входов в private и число конечных решений задаются отдельно условиями кампании и приватного оценщика.

## Решение и его происхождение

Регистрируй каждый предложенный кандидат до проверки. Неисправная программа, низкий балл и инфраструктурная ошибка не удаляют кандидата и не возвращают место в лимите. Исправленный код, новые параметры или объединение подходов — новое решение с новым ID. Технические повторы прежнего запроса остаются внутри проверки прежнего кандидата.

```bash
uv run python -m evaluator.search --journal runs/example/search.sqlite propose \
  --id solution-2 --directory cases/example/ways/solution-2 \
  --parent solution-1 --hypothesis 'Проверяемое объяснение ожидаемого эффекта' \
  --change 'Какие разрешённые компоненты изменены и почему' \
  --tokens 1200 --seconds 90
```

Для исходного кандидата не передавай `--parent`. Несколько `--parent` описывают объединение; неудачные кандидаты остаются допустимыми родителями. Родители должны уже существовать. Новая запись получает последовательный номер предложения и время. Повторная регистрация существующего ID отклоняется.

В базе сохраняется фактический снимок файлов, включая незакоммиченные изменения. В него должны входить код, промпты, скиллы и разрешённая изменяемая конфигурация; внешние зависимости фиксируй версией или digest в файлах кандидата. `digest` совпадает с `Candidate.digest()` приватного пакета и учитывает содержимое и список исполняемых файлов. Дополнительный `snapshot_digest` проверяет целостность архива. Git commit можно указать в описании изменения, но он не заменяет снимок и список родителей.

Локальный снимок не ограничен транспортными пределами private-пакета в 10 MiB и 1000 файлов. Несовместимость с контрактом пакета сохраняется как `bundle_error`; решение занимает место в лимите, сохраняет подготовительные расходы и родителей, допускает восстановление и train-проверки. Исправленная упаковка становится новым решением с прежним родителем.

`.git`, `.env`, симлинки и другие небезопасные файлы не сохраняются. Если безопасный снимок создать нельзя, предложение всё равно регистрируется: `snapshot_error` объясняет отказ, `digest` и `snapshot_digest` равны `null`, ресурсы, гипотеза и родство остаются в истории. Неполный снимок не объявляется восстановимым: `restore` и `begin` такого предложения запрещены, но оно может быть родителем исправленного решения. Ошибочные метаданные регистрации, повторный ID, отсутствующий родитель, исчерпанный лимит и остановка по-прежнему отклоняют саму команду. Не включай секреты или private в снимки, аргументы и журнал. SQLite обеспечивает согласованные операции, но не защищает от владельца, который напрямую переписывает файл базы.

`--tokens` и `--seconds` при предложении учитывают подготовку кандидата. Если токены известны не полностью, передавай измеренную часть и `--tokens-incomplete`; неизвестный расход не объявляется полным нулём. Нулевой полный расход здесь указывай только если сама подготовка не использовала LLM: генерация немодельной программы исследовательской моделью всё равно расходует токены.

Воспроизвести именно сохранённые файлы можно в новом каталоге:

```bash
uv run python -m evaluator.search --journal runs/example/search.sqlite restore \
  --candidate solution-2 --directory /tmp/solution-2-frozen
```

Запускай восстановленный снимок. Для новых записей с `digest_version: 2` восстановление и private создают одинаковую исполняемую форму: каталоги имеют права `0755`, обычные файлы — `0644`, исполняемые — `0755`. Пустые каталоги не входят в пакет; исходные права доступа и владельцы не переносятся. Поэтому снимок доступен контейнеру независимо от локального UID и umask. Если используешь рабочий каталог, предварительно проверь совпадение содержимого и исполняемых файлов с `digest` и этих условий исполнения. Проверка изменённого рабочего дерева под старым ID нарушает историю.

Старые записи без `digest_version: 2` проверяются по прежнему digest и целостности архива. Их восстановление сохраняет архивные пустые каталоги и права файлов (`mode & 0777`), чтобы не менять поведение старого решения; корень и каталоги получают `0755`. Старая форма может требовать прежнего UID для чтения или исполнения файла. Для нового сопоставления с private зарегистрируй новую версию решения, которая использует общий формат v2.

## Начало и завершение проверки

`begin` — атомарный допуск к запуску. Вызывай его непосредственно при запуске реальной проверки, не для постановки будущих проверок в очередь. Только успешный `begin` разрешает работнику стартовать. Журнал не управляет ОС-процессами; связь этих действий обеспечивает запускающий харнес или оркестратор.

```bash
uv run python -m evaluator.search --journal runs/example/search.sqlite begin \
  --id check-2 --candidate solution-2 --split train \
  --dataset dataset-v3 --subset validation-a --conditions metric-v2-fixed-conditions \
  --job 'local-process-or-cluster-job-id'
```

Ключ сопоставимости — точное сочетание `split`, `dataset`, `subset`, `conditions`. В `dataset` укажи версию данных, в `subset` — ссылку на сохранённый точный состав. `conditions` идентифицирует версию и digest замороженного пакета метрики, закреплённые зависимости и образ оценщика, модель и все остальные фиксированные условия проверки, включая fingerprint разрешённого реестра харнесов, если он используется. Сохрани полное описание условий в `campaign.md`, а в журнал передай его стабильный ID. Digest пакета доступен как `metric_package_provenance(path)["sha256"]` из `evaluator.metric_package`; абсолютный путь установки не входит в идентификатор пакета. Например, описание `metric-v2-fixed-conditions` связывает `metric_package_digest`, digest образа, lock зависимостей и фиксированные параметры модели. Это позволяет установить тот же пакет по разным путям для train и закрытых оценщиков. Разрешённые переменные эволюции входят в снимок решения, а не разбивают общую кривую на отдельные условия. При пустом public агент сам выбирает train-проверки; их результаты сопоставимы только внутри одинакового ключа.

Для завершения нужны либо корректный скалярный `--score`, либо `--error`. На train обязательны отдельные измеренные расходы решателя и оценщика:

Баллы и baseline используют конечные числа binary64. Значения целого типа и целые JSON-токены CLI за пределами `±(2**53 - 1)` отклоняются до преобразования, чтобы округление не создавало ложного равенства. Дробная и экспоненциальная запись интерпретируется как приближённый binary64. Нужную точность и шкалу задаёт метрика до кампании.

```bash
uv run python -m evaluator.search --journal runs/example/search.sqlite finish \
  --id check-2 --score 0.72 \
  --solver-tokens 2400 --solver-seconds 120 \
  --judge-tokens 800 --judge-seconds 30
```

На train расходы решателя включают подготовку к решению и все технические повторы этой проверки. Судейские расходы хранятся отдельно. Немодельные решатель и метрика указывают ноль токенов и фактическое время. `--solver-tokens-incomplete` и `--judge-tokens-incomplete` сохраняют неполноту учёта. Журнал дополнительно сохраняет внешне наблюдаемое время между `begin` и `finish`; это длительность проверки, а не время решения. Каждый передаваемый блок ресурсов требует оба значения: токены и секунды.

Train допускает `--evidence <file.json>` с произвольным JSON-объектом: ссылками на трейсы, анализом ошибок и дополнительными замерами. Public принимает только агрегированный балл; ресурсы и подробные свидетельства не передаются агенту и не допускаются в журнале. Для public поля `solver` и `judge` сохраняются как `null`, а не как выдуманные нули. Заверши такую проверку без ресурсных аргументов: `finish --id public-check --score 0.72`. Расходы подготовки из `propose` относятся к созданию кандидата и не раскрывают скрытую public-проверку. Для ошибки public разрешён только непрозрачный код `--error evaluation_failed`; детали остаются у доверенного оценщика. `private` не является допустимым разделом журнала.

Завершённая проверка неизменяема. Одновременно и после успеха нельзя запустить ещё одну проверку того же кандидата с тем же ключом сопоставимости ради нового балла. Не меняй идентификаторы условий для обхода этого правила. После технического сбоя допустим новый ID проверки с прежними входами, если протокол разрешает её продолжение; исправление решения требует нового кандидата. Ошибка без балла сохраняется вместе с доступными свидетельствами; на train обязательны фактические расходы, на public остаётся только непрозрачный код ошибки.

## Остановка

```bash
uv run python -m evaluator.search --journal runs/example/search.sqlite stop --reason 'Решение человека'
uv run python -m evaluator.search --journal runs/example/search.sqlite status
```

Явная остановка атомарно запрещает новые `propose` и `begin`. Уже начатые проверки завершаются через `finish`; `status.running` перечисляет их ID. Ожидай эти задания по общим правилам долгих прогонов. После остановки нет дополнительных проверок устойчивости, повторов завершённых серий или запусков ожидавшей очереди. Для отбора используются уже накопленные результаты и результаты завершившихся активных проверок.

Исчерпание `max_solutions` запрещает только следующие предложения: последнее допущенное решение ещё должно пройти свои проверки. Это отличается от досрочной команды человека. Отбор точного числа финалистов планируется заранее; журнал не подменяет заданное число меньшим и не выбирает финалистов автоматически.

## Данные для графика и AUC

```bash
uv run python -m evaluator.search --journal runs/example/search.sqlite export > runs/example/history.json
uv run python -m evaluator.search --journal runs/example/search.sqlite curve \
  --split train --dataset dataset-v3 --subset validation-a \
  --conditions metric-v2-fixed-conditions --direction maximize --baseline 0.1 \
  --horizon 1000 > runs/example/curve.json
```

`export` содержит предложения с родителями, гипотезами, снимочными digest и расходами подготовки; все проверки, включая ошибки; времена старта и завершения; независимый последовательный номер завершения и `proposal_count_at_finish`. Сами файлы снимков выдаются только через `restore`. Private-оценки в экспорт не попадают.

`curve` строит лучшую известную оценку по выбранному ключу. Для `maximize` сохраняется максимум, для `minimize` — минимум. Неудачи занимают места в оси предложений и сохраняют прежнее лучшее качество; отсутствие балла не превращается в ноль. При параллельной работе результат появляется в точке, равной числу уже предложенных решений **в момент завершения проверки**. Например, поздний результат кандидата №1, полученный после регистрации №10, не улучшает график задним числом в точке 1. Несколько завершений при одном количестве предложений сохраняют свой порядок, но имеют одинаковую координату X.

AUC — интеграл ступенчатой кривой: значение после события действует до следующего события; `integration = left_step`. `auc` хранит интеграл, `mean_quality = auc / horizon` — среднее качество на этом горизонте, `final_quality` — лучшее известное качество в конце. Направление сравнения остаётся направлением исходной метрики. Масштаб не нормируется к 0–1 и отрицательные оценки допустимы. Сравнивай AUC только при одинаковых данных, условиях, baseline, направлении и горизонте.

AUC отражает также организацию поиска: если все K предложений зарегистрированы до первого результата, AUC до K равна `baseline × K` независимо от конечного качества. Поэтому вместе с AUC указывай `final_quality`; для сравнения кампаний фиксируй сопоставимую политику параллелизма и регистрации предложений.

Переполнение представимого конечного интеграла AUC возвращает явную ошибку; шкалу метрики задают до кампании.

`--baseline` — явно зафиксированное качество при нуле предложений, уже известное до поиска. Не используй для него будущую оценку первого кандидата: она появляется в своей точке завершения. Без baseline полный `auc` и `mean_quality` равны `null`; `observed_auc`, `observed_from` и `covered_proposals` описывают только участок с известным качеством. Если ни одного качества нет, этот интеграл также `null`.

Без `--horizon` используется фактическое число предложений. Явный горизонт не может быть меньше него и позволяет сравнивать досрочно остановленный поиск на общем бюджете: последнее известное качество переносится до горизонта, новые решения при этом не выдумываются. `actual_proposals` хранится отдельно. Незавершённые проверки перечислены в `running`; такой экспорт пока предварительный. Экспорт не запускает никаких новых измерений.
