# Долгие прогоны и ожидание

Исследователь и оркестратор должны уметь ждать многочасовые и многодневные измерения без участия человека. Запускай train-прогон отдельным процессом или заданием кластера, которое продолжит работу после завершения вызова инструмента и отключения чата. Сохраняй ID задания, конфигурацию, число примеров, журналы, прогресс и результаты в файлах рабочей кампании. Выбирай доступный механизм запуска по его реальным гарантиям: один только фоновый `&` не гарантирует сохранение процесса после закрытия сессии.

## Как ждать прогон

1. После запуска сделай короткое первое ожидание, достаточное для появления первого полностью обработанного примера. Если пример ещё выполняется, проверь журнал запуска и увеличь следующее ожидание с учётом допустимой длительности одного примера. Отсутствие готового ответа само по себе не означает зависание.
2. После первого завершённого примера проверь, что решатель и выбранный оценщик работают, результаты и обязательные замеры сохраняются, процесс не завершился с ошибкой. Время примера должно включать подготовку, решение, все судейские оценки и повторы.
3. Вычисли оставшееся время по фактическому прогрессу: `remaining_seconds = elapsed_seconds / completed_examples * (total_examples - completed_examples)`. Для параллельного прогона используй прошедшее время всего задания и его общий счётчик готовых примеров. Добавь небольшой запас, например 15%, и сохрани расчёт вместе с моментом следующей проверки.
4. Засни на рассчитанное оставшееся время. Не возвращайся к рассуждению и проверке статуса в промежутке. Прогресс, ошибки и контрольные точки сохраняет сама программа, а не опрашивающая её модель. Если среда умеет доставлять событие завершения или ошибки, оно может разбудить агента раньше.
5. После ожидания прочитай итог. Если прогон ещё работает, пересчитай срок по новым данным и снова жди весь оставшийся интервал. Не превращай уточнение оценки в частый опрос.

Например, при 100 примерах и первом полном примере за 108 секунд оценка всего прогона составляет 3 часа, остаток — 2 часа 58 минут 12 секунд. После проверки первого результата ожидай весь этот остаток с запасом, без промежуточных обращений к модели ради статуса.

Используй штатное ожидание завершения процесса или субагента, длительный sleep либо планировщик пробуждения. Если один вызов ожидания короче расчётного срока, предпочти средство, способное ожидать весь срок без промежуточных вызовов модели. Когда среда этого не умеет, используй максимальное поддерживаемое ожидание и сохраняй состояние между необходимыми продолжениями; не имитируй непрерывную автономность обещанием, которого среда не обеспечивает. Промпт не увеличивает жёсткие лимиты платформы.

## Таймауты и повторы

Таймаут защищает от неограниченного зависания. Он должен покрывать медленную работу модели, очередь и повторы, а не обрывать нормальный длинный прогон. Значения по умолчанию для комплектного оценщика:

| Операция | Таймаут |
| --- | --- |
| Одна попытка обращения к решателю через gateway | 6 часов |
| Сетевые таймауты одной попытки судьи | 6 часов |
| Ожидание ответа gateway комплектным runner | 36 часов 13 минут 30 секунд |
| Подготовка контекста в комплектном харнесе | 48 часов |
| Один пример целиком внутри приватного runner | 7 суток |
| HTTP-запрос клиента к приватному оценщику | 1 час |

Для одного модельного запроса предусмотрена первая попытка и ещё пять повторов при ошибке. Между повторами выдерживаются 30, 60, 120, 240 и 300 секунд. Клиент, ожидающий gateway, должен покрывать все шесть попыток, все паузы и запас на передачу результата. Настройки задаёт оператор через env по [инструкции развёртывания](../deploy/README.md); они фиксируются до начала кампании.

Gateway ограничивает общую длительность отдельной попытки. Встроенный судья `llm` использует сетевые таймауты подключения и обмена; это не строгий предел полного времени запроса, если данные продолжают поступать. Для собственной модельной команды gateway ограничивает попытки, а `command.timeout_seconds` — весь процесс со всеми запросами. При подготовке выбирай этот таймаут под полную процедуру оценки и повторы.

Общего таймаута всей серии в комплектном оценщике нет. Таймаут HTTP-запроса `submit/status` относится к передаче запроса и получению ответа сервиса, а не к обработке датасета после `202 running`.

Повторяются транспортные и HTTP-ошибки, некорректный JSON или схема, пустой либо обрезанный ответ. Вход, модель и параметры остаются прежними. Корректный ответ с низкой оценкой не повторяется. Для встроенной модельной метрики судья должен получить `votes` корректных независимых оценок каждого критерия; число задаётся метрикой, по умолчанию равно 3. Технические ошибки этих запросов не считаются голосами. Собственная метрика следует своей зафиксированной процедуре. Модельная команда использует повторы gateway и не добавляет поверх них ещё один цикл технических повторов. После исчерпания повторов сохраняется явный сбой. Не открывай новую приватную попытку и не меняй состав кандидатов, чтобы обойти ошибку.

Для train-харнеса, запуска инструментов и ожидания субагентов выставляй столь же длинные таймауты. Предел всего задания должен покрывать весь набор, подготовку, судейство и возможные повторы; он не должен быть короче рассчитанной длительности прогона. Не останавливай субагента только из-за длительного молчания: реализация метода и проверка модели могут занимать дни. Получай его итог штатным ожиданием или событием завершения. Лимит числа предложенных решений сохраняется; длительный таймаут не разрешает новые решения сверх него. Измеряемые токены и время не являются дополнительными лимитами поиска.

## Остановка и закрытые проверки

Явная команда человека остановить поиск прерывает ожидание для передачи команды работникам и фиксации остановки. Новые предложения, новые проверки и ожидающие запуска проверки не начинаются. Уже выполняющиеся проверки завершаются; их результаты сохраняются, после чего отбор использует накопленные свидетельства. Не запускай дополнительные проверки ради отбора. Достижение лимита предложений само по себе не отменяет плановые проверки уже зарегистрированных решений.

Пустой раздел не запускается и не получает нулевой score. Если ещё нет завершённого примера, не вычисляй ETA делением на ноль: используй допустимую длительность примера и события задания. При public/private-проверке исследователь не читает первый пример или трейс: исправность и прогресс проверяет закрытый процесс, а агент использует разрешённый статус и заранее оценённую длительность.

Public-сервис принимает по одному кандидату и запускает работника до ответа `202`, без очереди в общем пуле исполнения. Пакеты из нескольких public-кандидатов отклоняются. Запись `begin` означает непосредственную отправку проверки, не постановку в очередь. Остановка поиска прекращает новые отправки; работники принятых проверок завершаются. Работники принадлежат процессу сервиса: его перезапуск прерывает их, а незавершённые записи получают `failed`.

После принятия private-пакета оценщик сам выполняет серию и выбирает заданное число лучших решений. Эволюционный агент не управляет отдельными примерами и получает только статус; все результаты читает оператор внутри закрытого контура. Оцени длительность по сопоставимому train-прогону и известному размеру серии либо используй заданный оператором интервал. Не опрашивай API по примерам. Для продолжения достаточно работающего сервиса; чат можно закрыть. Перезапуск оценщика не возобновляет прерванную серию.

## Настройка среды пользователем

Перед длительной кампанией увеличь доступные таймауты инструментов, время жизни заданий и сессий. Если выбранная среда поддерживает настройку глубины или вложенности субагентов, увеличь её, чтобы исследователь мог делегировать реализацию, анализ и проверки. Выбери технические пределы по длительности работы и доступной среде. Эти инструкции описывают поведение агентов; отдельного планировщика кампаний или автоматического восстановления сессий в репозитории нет. Журнал поиска учитывает лимит предложений и остановку; он не управляет процессами работников.
