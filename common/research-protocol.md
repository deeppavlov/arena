# Протокол исследования

Арена ищет переносимый способ решения кейса. Конкретная задача, критерии и допустимые способы изменения задаются кейсом. Упоминания отдельных подходов в `ways/` — стартовые гипотезы, а не обязательная архитектура.

До первого замера зафиксируй версию public/private-разделения, постановку и входы, критерии и веса, подготовленные эталоны, baseline, правило отбора, модель, харнес решателя, настройки генерации и ограничения ресурсов. Модель решателя и судьи одна и та же; вызовы разделены по контексту. Все модельные операции над public и private выполняются внутренними моделями. Инструмент, из которого человек управляет кампанией, этого ограничения не меняет.

В ходе кампании меняются только разрешённые кейсом части кандидата. Модель, харнес, критерии и оценщик не являются предметом оптимизации. Изменение фиксированных условий означает новую кампанию; результаты разных условий не объявляются прямым сравнением.

## Public-цикл

1. Эксперты проверяют постановку, наличие входов и критериев, воспроизводимость baseline. Пробелы отмечаются явно.
2. Исследователь формулирует механизм, ожидаемый эффект, область применимости и проверку, способную опровергнуть гипотезу.
3. Оркестратор разводит независимые направления по работникам. Каждый работает в своей ветке и сохраняет findings.
4. Для разведки разрешены небольшие public-подмножества. Сохраняются точные ID и способ выбора; результат на выбранных удобных примерах не выдаётся за результат на всём наборе.
5. Для одного примера кандидат создаёт **один корректно полученный ответ**. Этот ответ оценивается **три раза по каждому критерию, отдельным запросом для каждого критерия**. При `C` критериях это `3 × C` корректных оценок судьи, а не три решения и не один запрос со всеми критериями. Техническая ошибка любого обращения допускает до пяти повторов с тем же входом и настройками; невалидный ответ судьи не считается голосом.
6. Сохраняются версия кандидата, параметры, public-трейсы, баллы каждого запроса, ошибки и обязательные замеры токенов и времени решения. Учитываются подготовка, все модельные вызовы харнеса и повторные попытки. Судейские затраты записываются отдельно; неизвестная стоимость или usage остаются явно неизвестными. MLflow используется для просмотра и сравнения; отсутствие MLflow не оправдывает потерю локальных свидетельств.
7. По трейсу ищется причина класса ошибок согласно [IMMUNE](IMMUNE.md). Следующее изменение проверяется и на других примерах. Неудачный подход сохраняется как отрицательный результат.

Судейство — абсолютная оценка по заранее подготовленному синтетическому эталону. Его подготовка по `prompts/prepare-reference.md` и проверка отделены от поиска кандидатов; он не дописывается под оцениваемый ответ. Судье передаются только материалы, предусмотренные версией метрики; A/B-сравнение кандидатов не используется. Критерий формулируется отдельным вопросом со своей шкалой. Код усредняет три оценки каждого критерия, затем считает взвешенное среднее с делением на сумму весов; результат кандидата — среднее по примерам.

Инфраструктурный сбой и невалидный ответ судьи не доказывают низкое качество кандидата. После пяти повторов их статус остаётся явным; нельзя незаметно удалить неудобный пример или заменить пропуск нулём. На public документированный повтор после сбоя не является разрешением заново генерировать ответ ради лучшего балла. Используй длинные таймауты и [протокол ожидания](long-runs.md): проверь первый завершённый пример, оцени длительность остатка и ожидай её целиком. Сам прогон сохраняет локальные результаты и прогресс без постоянного участия исследователя.

## Финал

Перед отбором кандидаты измеряются на одном заранее зафиксированном public-наборе, с одинаковыми условиями и полным учётом ошибок. Разведочные оценки разных подмножеств в одну рейтинговую таблицу не смешиваются. Ранжирование едино для public и private: выше балл, затем полный учёт токенов решателя, затем меньше токенов среди полных замеров, затем меньше времени решения, затем стабильный порядок `candidate_id`. Между замерами с неизвестной частью токенов сравнивается время, а известная сумма не выдаётся за полный расход. Ревью проверяет обобщаемость изменений, отсутствие lookup готовых ответов на оценочные задания, воспроизводимость и ограничения. Индексация исходного корпуса и явно разрешённое кейсом обучение на public сами по себе не являются утечкой; их условия фиксируются до сравнения.

Оркестратор выбирает зафиксированное оператором число финалистов, по умолчанию пять (допустимо от одного до пяти), фиксирует их содержимое и отправляет весь список на private один раз. Число, список, код, конфигурации и ресурсы заморожены до первого допуска. Нельзя сначала получить оценку одного кандидата, затем выбрать, поправить или исключить остальных. Нельзя переименовать тот же кандидат или кампанию, чтобы обойти лимит допуска.

Private-оценщик сам запускает замороженные артефакты. Исследователь не получает private-вопросы, эталоны, ответы, трейсы, отдельные оценки примеров или промежуточные результаты серии. Допуск каждого финалиста однократный. Повторная доставка того же списка идемпотентна: возвращает существующее состояние и не запускает оценку заново. При инфраструктурном сбое допуск остаётся израсходованным, частичные результаты закрыты; после перезапуска незавершённая серия получает `failed`. API не возобновляет её и не сбрасывает квоту. Причину может изучить только оператор в изолированном контуре. Итоговые агрегированные оценки раскрываются только после успешного завершения всей серии.

Результат — замороженный лучший кандидат, его измерения и ограничения. Победа на private не запускает внедрение автоматически. На закрытый набор разрешён один релиз результатов; после него набор закрывается для новых допусков (`sealed`). Следующий виток оптимизации требует нового private-набора, а не нового названия кампании.

Победителя предыдущей кампании можно измерить отдельно как контрольную нижнюю границу на новых данных. Не передавай его код исследователям как стартовую ветвь нового поиска: это другое условие эксперимента, которое нужно согласовать и обозначить отдельно. Равенство лучших итоговых оценок разрешается по замеренным ресурсам, без изменения кандидатов и дополнительных private-попыток.
