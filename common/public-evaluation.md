# Единая оценка и ранжирование

Версия метрики определяет способ вычисления и направление улучшения: `maximize` или `minimize`. Один и тот же измеритель применяется на train, public и private. Различается доступ к результатам: train полностью открыт для исследования, public возвращает агенту только общий score кандидата, private сохраняет все результаты для оператора. Пустой train или public не запускается и не заменяется выдуманным нулём.

Для train агент выбирает наборы и схему валидации, сохраняя точные ID и условия. Для прямого сравнения и одной кривой используй один и тот же набор и версии условий. Дополнительные разведочные проверки хранятся отдельно. Если промпт разрешает поиск харнеса или параметров, их различия входят в кандидат; остальные условия сравнения остаются фиксированными.

## Способ вычисления

В `evaluator.contracts.Metric` поле `kind` выбирает реализацию:

- `llm`: профиль с синтетическим эталоном, инструкцией и критериями;
- `command`: зафиксированная оператором программа, вычисляющая численную оценку без обязательного обращения к LLM.

Общая точка входа — `evaluator.metrics.evaluate_answer(metric, example, answer, complete=None)`. Для `llm` ей передаётся внутренний модельный клиент; для `command` он не нужен. Ответ решателя — один корректно полученный результат на пример в рамках данной проверки; выбор лучшего из повторных корректных ответов запрещён. Сам решатель может быть модельным или немодельным при любом способе оценки.

Для `command` оператор задаёт `command.argv`, `command.source_sha256` и `command.timeout_seconds`. Команда получает JSON с `example` и `answer` через stdin и возвращает через stdout JSON `{"score": число}`; при необходимости она добавляет объект `statistics` для агрегации. Допустима конечная положительная, нулевая или отрицательная оценка. Исполняемый файл и файлы реализации фиксируются хешами, зависимости и среда входят в условия кампании. Код метрики не берётся из кандидата и не меняется во время поиска. Ошибка программы или невалидный ответ сохраняются как ошибка проверки, а не как score кандидата.

По умолчанию `evaluator.metrics.aggregate_results(metric, results)` усредняет оценки всего заданного набора. Для иной метрики уровня набора оператор задаёт `Metric.aggregation` — такую же зафиксированную команду. Она получает JSON `{"results": [...]}` с записями примеров, включая `statistics`, и возвращает `{"score": число}`. При ошибке нельзя усреднять только успешную часть или незаметно удалять пример. Способ агрегации и направление фиксируются до поиска; время агрегатора входит в отдельные расходы оценщика.

## Профиль с модельным судьёй

`synthetic-reference-per-criterion-v1` использует синтетический эталон, подготовленный до кампании по [промпту](../prompts/prepare-reference.md). Судья получает инструкцию задачи, один критерий, эталон и оцениваемый ответ. Он не получает вход с исходниками, чужие голоса, веса или второй ответ для A/B-сравнения. Судья использует зафиксированную внутреннюю модель. Если решатель также использует LLM, это та же модель; запросы и контексты разделены.

Для каждого критерия нужны три независимые корректные целые оценки 1–5. При технической ошибке модельного запроса допускается до пяти повторов с прежними входом и настройками. Дополнительная попытка не является новым голосом, решением или разрешением улучшить уже корректный ответ. Балл критерия — среднее голосов; балл примера — взвешенное среднее критериев с делением на сумму весов. Стандартная шкала этого профиля максимизируется; минимизация допустима только с явно заданным преобразованием через агрегатор.

Пустой ответ модельного API повторяется как ошибка. Штатный пустой окончательный ответ харнеса получает 0 без вызова судьи только в этом профиле. Вычисляемая метрика сама определяет значение пустого ответа. Инфраструктурный сбой после исчерпания повторов остаётся явным сбоем.

Используй `ModelClient` из `evaluator.judge` с параметрами кампании и внутренним endpoint. Его `usage` и `elapsed_seconds` накапливаются за всё время жизни, включая повторы и паузы. При переиспользовании клиента сохраняй разность счётчиков до и после примера. Сохраняй ресурсы и при ошибке. Правила таймаутов и ожидания — в [long-runs.md](long-runs.md).

## Замеры ресурсов

Для каждого примера измеритель сохраняет отдельные записи `resources.solver` и `resources.judge`. Каждая содержит `wall_seconds` и вложенный `usage` с `prompt_tokens`, `completion_tokens`, `total_tokens`, `attempts`, `unreported_attempts`. Время решателя измеряется снаружи харнеса от начала подготовки до окончательного ответа, включая инструменты, модельные вызовы и повторы. Usage собирается из ответов модельного сервера для всех обращений; собственное заявление кандидата расходом не считается.

Если модельных вызовов не было, токены и попытки равны нулю, время всё равно измеряется. Для вычисляемой немодельной метрики токены оценщика также нулевые. Если попытка не вернула корректный usage, увеличивается `unreported_attempts`, а известные токены остаются неполной суммой. Неизвестный usage нулём не заменяется.

По одному завершённому набору суммируй `solver_tokens`, `solver_seconds`, `solver_unreported_attempts`; отдельно — `judge_tokens`, `judge_seconds`, `judge_unreported_attempts`. Затраты на подготовку входят в учёт; общую подготовку и способ её отнесения к решениям зафиксируй до сравнения. Поиск не ограничивается токенами или временем, но расходы не теряются.

Train-измерения, ответы и трейсы можно сохранять локально и в [MLflow](mlflow.md). На public ресурсы и подробности остаются в закрытом контуре вместе с данными; агент получает только общий score. Private-измерения не передаются агенту даже после завершения. Повторная доставка сохранённых логов не запускает решение или оценку снова.

## Правило ранжирования

```python
from evaluator.ranking import choose_winners

winners = choose_winners(candidate_scores, count=output_count, direction=metric.direction)
```

Каждая строка `candidate_scores` содержит `candidate_id`, `score`, `solver_tokens`, `solver_seconds` и `solver_unreported_attempts`. Функция возвращает ровно `count` идентификаторов в порядке ранга. `choose_winner` остаётся вариантом для одного результата.

Сначала сравнивается качество в направлении метрики. При равенстве предпочтительнее полный учёт токенов; среди полных замеров — меньше токенов, затем меньше времени решения. Если у обоих кандидатов расход токенов неполный, сравнивается время. Полное равенство разрешается стабильным порядком `candidate_id`. Немодельное решение с полным нулевым расходом токенов выигрывает у модельного при равном качестве. Затраты оценщика не участвуют в ранжировании.

Это правило выбирает конечные N на private и позволяет сравнивать сопоставимые train-замеры. Входной набор private выбирается отдельно по полезности: качество, разнообразие, устойчивость и риск переобучения учитываются по накопленным свидетельствам. Он не обязан совпадать с top-K рейтинга. Данные кривой эволюции и AUC описаны в [search-history.md](search-history.md); private всех промежуточных решений для них не проверяется.
