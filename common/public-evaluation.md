# Единая оценка и ранжирование

Версия метрики определяет способ вычисления и направление улучшения: `maximize` или `minimize`. Один и тот же измеритель применяется на train, public и private. Различается доступ к результатам: train полностью открыт для исследования, public возвращает агенту только общий score кандидата, private сохраняет все результаты для оператора. Любой раздел может быть пустым; его оценивание не запускается и не заменяется выдуманным нулём. При пустом private нет закрытого ранжирования; итоговый выбор сохраняется по условиям кампании и доступным свидетельствам.

Для train агент выбирает наборы и схему валидации, сохраняя точные ID и условия. Для прямого сравнения и одной кривой используй один и тот же набор и версии условий. Дополнительные разведочные проверки хранятся отдельно. Если промпт разрешает поиск харнеса или параметров, их различия входят в кандидат; остальные условия сравнения остаются фиксированными.

Оценка измеряет качество ответа по замороженной метрике, но не удостоверяет допустимость реализации кандидата. Происхождение train-подсказок, соблюдение области изменений и риск переобучения проверяются отдельно по [протоколу исследования](research-protocol.md) и [промпту ревью](../prompts/reviewer.md). Измеренный score сохраняется в истории даже при обнаруженном нарушении; это не разрешает допуск кандидата на private. Очищенная от подсказок версия получает собственные ID, снимок и измерения, прежний балл на неё не переносится.

## Способ вычисления

В `evaluator.contracts.Metric` поле `kind` выбирает реализацию:

- `command`: собственная программная, модельная или смешанная оценка;
- `llm`: готовый профиль с синтетическим эталоном, инструкцией и критериями.

Общая точка входа — `evaluator.metrics.evaluate_answer`. Для `llm` ей передаётся внутренний модельный клиент `complete`; для модельной команды — `model_access` и общий счётчик `usage`. Программная команда работает без модельного доступа. Ответ решателя — один корректно полученный результат на пример в рамках данной проверки; выбор лучшего из повторных корректных ответов запрещён. Сам решатель может быть модельным или немодельным при любом способе оценки.

Агент подготовки создаёт пакет в `cases/<case>/metric/` по [протоколу подготовки](preparation.md). Например, переносимая программная метрика содержит `metric.json` и `score.py`:

```json
{
  "version": "my-metric-v1",
  "kind": "command",
  "direction": "maximize",
  "command": {
    "argv": ["python", "score.py"],
    "uses_model": false,
    "timeout_seconds": 21600
  }
}
```

В переносимом пакете команды ссылаются на файлы внутри него; абсолютные пути и выход через `..` не допускаются. `python` и `python3` разрешаются в интерпретатор окружения оценщика. Загрузчик проверяет состав и исполняемость файлов по lock-файлу и преобразует пути. Путь к ресурсу передавай отдельным аргументом, например `["python", "score.py", "--config", "policy.json"]`. Запускаемая команда имеет рабочий каталог `/`; свои материалы ищи относительно файла программы, например через `Path(__file__).parent`. Зависимости и среду фиксирует оператор. Для прежнего формата `metric.json` оператор задаёт абсолютные `argv` самостоятельно.

Команда получает JSON через stdin:

```json
{"example":{"id":"check-1","input":"Вход","reference":"Эталон или null"},"answer":"Ответ решателя"}
```

Результат stdout — один JSON `{"score": 1.0}` с необязательным объектом `statistics`. Допустим конечный положительный, нулевой или отрицательный score. При заданном `aggregation` команда может вернуть только `{"statistics": {...}}`; итоговый агрегатор обязан выдать численный score. Без агрегатора каждый пример обязан иметь score. Сообщения для диагностики направляй в stderr. Рабочие примеры находятся в [шаблоне кейса](../cases/template/README.md).

Для модельной или смешанной команды задай `uses_model: true`. Дополнительно в stdin придут `model`, `model_base_url` и `model_request_timeout`: фиксированная модель, временный адрес gateway с допуском только к этому запуску и таймаут ожидания одного полного запроса. Используй `model_base_url + "/chat/completions"`; не выбирай другую модель, не обращайся к внешним endpoint и не передавай операторский ключ. Число запросов, критерии, проверка ответов и вычисление результата определяются программой метрики. Gateway выполняет технические повторы; отключи дополнительные повторы SDK. `uses_model: false` не получает модельный допуск.

`command.timeout_seconds` ограничивает весь процесс оценки, включая все обращения, повторы и агрегацию внутри этой команды. Агент подготовки выбирает его под процедуру; умолчание 21600 секунд может быть недостаточно для длинного модельного судейства. `model_request_timeout` покрывает все попытки одного запроса gateway. Это технические таймауты отдельных операций; общая длительность поиска ими не ограничивается. Код метрики не берётся из кандидата и не меняется во время поиска. Ошибка программы или невалидный ответ сохраняются как ошибка проверки, а не как score кандидата.

Оценки представлены конечными числами IEEE 754 binary64: дробные значения и арифметика имеют соответствующую точность, произвольная точность не поддерживается. Целые входные оценки допускаются только в диапазоне от `-(2**53 - 1)` до `2**53 - 1`; большие целые отвергаются до преобразования, а не округляются до ничьей. Это правило применяется к команде, агрегатору, рейтингу и журналу поиска. Дробная и экспоненциальная запись явно задают приближённое значение. Если задача требует различать соседние большие целые, выбери подходящую шкалу метрики до кампании; простое преобразование в float не сохраняет эти различия.

Команда выполняется в отдельной POSIX-группе процессов. При таймауте, ошибке и нормальном завершении оставшиеся процессы группы получают `SIGKILL`; оценщик дожидается прямого процесса, а на Linux — также остановки остальных живых участников группы. Время очистки входит в расходы оценщика. Доверенная программа метрики не должна переводить потомков в другие группы или сессии; этот механизм не является изоляцией недоверенного кода.

Максимальный JSON-ответ команды — 1 MiB. Вывод поступает во временные файлы и читается с ограничением объёма. При ошибке закрытый журнал содержит команду, код завершения, признак таймаута и первые 64 KiB stdout и stderr с отметками усечения; некорректные UTF-8 байты заменяются при декодировании. Эти диагностические данные на public и private доступны только оператору. Они сохраняются также для невалидного JSON и ошибок агрегатора.

По умолчанию `evaluator.metrics.aggregate_results(metric, results)` усредняет оценки всего заданного набора. Для иной метрики уровня набора оператор задаёт `Metric.aggregation` — такую же зафиксированную команду, включая собственный `uses_model`. Она получает JSON `{"results": [...]}` и возвращает `{"score": число}`. Записи набора содержат `example_id`, сохранённый `answer`, результат оценки, включая `statistics`, и измеренные `resources`; train-адаптер формирует ту же структуру, что закрытый оценщик. Для модельного агрегатора в stdin добавляются те же поля модельного доступа. При ошибке нельзя усреднять только успешную часть или незаметно удалять пример. Способ агрегации и направление фиксируются до поиска; время и модельные обращения агрегатора входят в расходы оценщика.

Учёт модельных команд собирается доверенным gateway, включая повторы и завершившиеся ошибкой обращения. Самоотчёт программы о расходе токенов не используется. Допуск закрывается после команды; неполные замеры сохраняются как неполные. Полный `model_base_url` содержит секрет: не печатай вход целиком и не сохраняй URL в результатах, статистике или HTTP-трейсах.

## Профиль с модельным судьёй

`synthetic-reference-per-criterion-v1` использует синтетический эталон, подготовленный до кампании по [промпту](../prompts/prepare-reference.md). Судья получает инструкцию задачи, один критерий, эталон и оцениваемый ответ. Он не получает вход с исходниками, чужие голоса, веса или второй ответ для A/B-сравнения. Судья использует зафиксированную внутреннюю модель. Если решатель также использует LLM, это та же модель; запросы и контексты разделены.

Для каждого критерия нужны `votes` независимых корректных целых оценок 1–5. `votes` — положительное целое поле метрики, по умолчанию 3. При технической ошибке модельного запроса допускается до пяти повторов с прежними входом и настройками. Дополнительная попытка не является новым голосом, решением или разрешением улучшить уже корректный ответ. Балл критерия — среднее голосов; балл примера — взвешенное среднее критериев с делением на сумму весов. Стандартная шкала этого профиля максимизируется; минимизация допустима только с явно заданным преобразованием через агрегатор. Иная шкала или процедура реализуется собственной командой.

Пустой ответ модельного API повторяется как ошибка. Штатный пустой окончательный ответ харнеса получает 0 без вызова судьи только в этом профиле. Вычисляемая метрика сама определяет значение пустого ответа. Инфраструктурный сбой после исчерпания повторов остаётся явным сбоем.

Используй `ModelClient` из `evaluator.judge` с параметрами кампании и внутренним endpoint. Его `usage` и `elapsed_seconds` накапливаются за всё время жизни, включая повторы и паузы. При переиспользовании клиента сохраняй разность счётчиков до и после примера. Сохраняй ресурсы и при ошибке. Правила таймаутов и ожидания — в [long-runs.md](long-runs.md).

## Тот же пакет на train

Штатный `evaluator.train` предоставляет общий сервис и CLI `serve`, `submit`, `status`, `result` по [инструкции развёртывания](../deploy/README.md#необязательный-train-сервис-и-подготовка-материалов). Новый кейс задаёт данные в формате `Example` JSONL, пакет метрики, совместимый runner и конфигурацию; отдельный train-адаптер нужен только для интеграции, не покрытой общим контрактом. Сервис загружает замороженный пакет через `load_metric`, оценивает единственный сохранённый ответ каждого примера через `evaluate_answer` и завершает весь набор через `aggregate_results`. Он измеряет решатель и метрику отдельно, сохраняет результат каждого этапа, включая сбои. Условия в [журнале поиска](search-history.md) содержат версию пакета и закреплённую среду, а не локальный путь установки.

Этот пример проверяет программный пакет шаблона на одном синтетическом ответе; собственная интеграция подставляет сохранённые `Example` и ответ решателя:

```python
import json
from pathlib import Path
from time import perf_counter

from evaluator.contracts import Example
from evaluator.metric_package import load_metric, metric_package_provenance
from evaluator.metrics import aggregate_results, evaluate_answer
from evaluator.reliability import empty_usage

package = Path("runs/my-campaign/metric")
metric = load_metric(package)
usage = empty_usage()
example = Example(id="synthetic-1", input="Тест", reference="ответ")
answer = "ответ"
started = perf_counter()
result = evaluate_answer(metric, example, answer, usage=usage)
example_seconds = perf_counter() - started
example_usage = usage.copy()
started = perf_counter()
score = aggregate_results(metric, [{
    "example_id": example.id, "answer": answer, **result,
    "resources": {
        "solver": {"wall_seconds": 0.0, "usage": empty_usage()},
        "judge": {"wall_seconds": example_seconds, "usage": example_usage},
    },
}], usage=usage)
aggregation_seconds = perf_counter() - started
aggregation_usage = {key: usage[key] - example_usage[key] for key in usage}
print(json.dumps({
    "metric_package": metric_package_provenance(package),
    "score": score,
    "judge": {"wall_seconds": example_seconds, "usage": example_usage},
    "aggregation": {"wall_seconds": aggregation_seconds, "usage": aggregation_usage},
    "judge_total": {
        "wall_seconds": example_seconds + aggregation_seconds,
        "usage": usage,
    },
}, ensure_ascii=False))
```

Для собственной модельной команды создай `MetricModelAccess` из `evaluator.metrics` с `model`, `base_url` и `usage_dir`; при необходимости укажи закреплённые `model_timeout` и `retry_delay`. `base_url` — доступный train-процессу адрес внутреннего gateway с окончанием `/v1`; `usage_dir` — его общий доверенный каталог учёта. Передавай один `model_access` и тот же накопительный `usage` в **оба** вызова: `evaluate_answer(..., model_access=access, usage=usage)` и `aggregate_results(..., model_access=access, usage=usage)`. Разность счётчиков даёт расходы примера или агрегатора. На сбое сохраняй уже накопленные расходы в `finally`; не заменяй ошибку score. Доступ к каталогу учёта выдаётся адаптеру, не кандидату. Для встроенного `llm` используй описанный выше `ModelClient` и его счётчики.

## Замеры ресурсов

Для каждого примера измеритель сохраняет отдельные записи `resources.solver` и `resources.judge`. Каждая содержит `wall_seconds` и вложенный `usage` с `prompt_tokens`, `completion_tokens`, `total_tokens`, `attempts`, `unreported_attempts`. Время решателя измеряется снаружи харнеса от начала подготовки до окончательного ответа, включая инструменты, модельные вызовы и повторы. Usage собирается из ответов модельного сервера для всех обращений; собственное заявление кандидата расходом не считается.

Если модельных вызовов не было, токены и попытки равны нулю, время всё равно измеряется. Для вычисляемой немодельной метрики токены оценщика также нулевые. Если попытка не вернула корректный usage, увеличивается `unreported_attempts`, а известные токены остаются неполной суммой. Неизвестный usage нулём не заменяется.

По одному завершённому набору суммируй `solver_tokens`, `solver_seconds`, `solver_unreported_attempts`; отдельно — `judge_tokens`, `judge_seconds`, `judge_unreported_attempts`. Затраты на подготовку входят в учёт; общую подготовку и способ её отнесения к решениям зафиксируй до сравнения. Поиск не ограничивается токенами или временем, но расходы не теряются.

Train-измерения, ответы и трейсы можно сохранять локально и в [MLflow](mlflow.md). На public ресурсы и подробности остаются в закрытом контуре вместе с данными; агент получает только общий score. Private-измерения не передаются агенту даже после завершения. Повторная доставка сохранённых логов не запускает решение или оценку снова.

## Правило ранжирования

```python
from evaluator.ranking import choose_winners

winners = choose_winners(candidate_scores, count=output_count, direction=metric.direction)
```

Каждая строка `candidate_scores` содержит `candidate_id`, `score`, `solver_tokens`, `solver_seconds` и `solver_unreported_attempts`. Функция возвращает ровно `count` идентификаторов в порядке ранга. `choose_winner` остаётся вариантом для одного результата.

Сначала сравнивается качество в направлении метрики. При равенстве предпочтительнее полный учёт токенов; среди полных замеров — меньше токенов, затем меньше времени решения. Если у обоих кандидатов расход токенов неполный, сравнивается время. Полное равенство разрешается стабильным порядком `candidate_id`. Немодельное решение с полным нулевым расходом токенов выигрывает у модельного при равном качестве. Затраты оценщика не участвуют в ранжировании.

Это правило выбирает конечные N на private и позволяет сравнивать сопоставимые train-замеры. Входной набор private выбирается отдельно по полезности: качество, разнообразие, устойчивость и риск переобучения учитываются по накопленным свидетельствам. Он не обязан совпадать с top-K рейтинга. Данные кривой эволюции и AUC описаны в [search-history.md](search-history.md); private всех промежуточных решений для них не проверяется.
