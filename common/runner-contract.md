# Харнес и кандидат

Оператор до кампании фиксирует реестр доступных харнесов: идентификатор, образ по `sha256`, режим использования модели и доверенную конфигурацию запуска. Промпт кампании определяет, что разрешено менять: само решение при фиксированном харнесе либо харнес и его параметры при фиксированном решении. Один кандидат исполняется с одинаковой конфигурацией на train, public и private. Модель и её параметры остаются фиксированными там, где модель используется.

Кандидат может содержать `solution.json`:

```json
{"harness":"registered-id","parameters":{"depth":4}}
```

`harness` выбирается из операторского реестра, а смысл и допустимые значения `parameters` определяют адаптер и промпт кампании. Возможности `supports_build` и `supports_asset_selection` объявляет оператор отдельно для каждого харнеса; обе по умолчанию отключены. Только при включённом `supports_asset_selection` параметр `asset_digests` принадлежит инфраструктуре. Иначе наличие `build.py` и одноимённого параметра не включает новые правила и не требует квитанции подготовки. Если файла нет, используется харнес по умолчанию. Кандидат не выбирает произвольный образ, команды контейнера, mounts, модель или адрес её сервера. Код решения, manifest и параметры входят в неизменяемый пакет кандидата; новый вариант получает собственный ID и запись родителей в журнале кампании.

## Протокол запуска

Для каждого закрытого примера оценщик создаёт новый контейнер. В нём:

- `/candidate` — readonly-файлы замороженного пакета;
- `/assets` — необязательные readonly-материалы, разрешённые всем решениям;
- `/tmp` — ограниченная временная память;
- stdin — JSON в UTF-8 размером не более 8 MiB с `input`, необязательной `operation: "solve"`, `prepare_timeout` и необязательным объектом `parameters`; немодельный харнес получает `uses_model: false`, модельный — фиксированную `model`, адрес `model_base_url` вида `http://model-gateway:8081/runs/<run_id>/<capability>/v1` и `model_request_timeout`; таймауты задаются в секундах;
- stdout — один JSON `{"answer":"окончательный ответ"}` размером не более 1 MiB.

Оценщик передаёт компактный JSON без ASCII-экранирования корректного Unicode и проверяет размер до запуска контейнера. Предел входа вмещает разрешённые 500 000 символов примера, включая управляющие символы, и параметры из `solution.json` размером до 1 MiB, включая их расширение при сериализации чисел. Предел ответа остаётся независимым от размера задания. Сторонний адаптер должен поддерживать те же пределы.

Модельный gateway принимает запрос до 16 MiB: в нём помещаются вход примера, промпт и подготовленный контекст с учётом JSON-экранирования. Ответ внутренней модели ограничен 2 MiB; комплектный runner по-прежнему читает не более 1 MiB ответа gateway. Эти транспортные пределы не меняют ограничения контекста выбранной модели.

Ненулевой exit, timeout, переполнение или неверный JSON означают сбой выполнения: закрытая серия останавливается без публикации частичного результата. Неудачный кандидат остаётся решением в журнале кампании и может быть родителем следующего. Штатный пустой ответ обрабатывает выбранная метрика; комплектный LLM-судья даёт ему 0. Пустой или обрезанный ответ модельного API считается ошибкой запроса и сначала проходит до пяти повторов.

Эталон, соседние примеры, оценки, операторские секреты и закрытые журналы контейнеру не передают. Немодельный харнес запускается с `network=none`, без gateway и модельных реквизитов. Для модельного харнеса разрешена только выделенная внутренняя сеть с gateway, который пропускает вызовы фиксированной модели. В эту сеть не входят оценщик, исследователь и MLflow.

`model_base_url` содержит отдельный случайный 256-битный секрет допуска только к учёту этого запуска. Он передаётся через stdin; имя контейнера и UUID доступа не дают. Gateway проверяет секрет до открытия модельного запроса и изменения счётчиков, а после завершения контейнера допуск закрывается. В доверенном журнале хранится только хеш секрета. Харнес и подготовка используют переданный URL целиком; старый путь только с UUID отклоняется. Полный URL, включая секрет, не сохраняют в трейсы, ошибки, argv, env или общий MLflow. Комплектный gateway отключает access log; сторонние клиенты и прокси должны скрывать секретный сегмент пути до записи логов.

## Комплектный пример

В модельном режиме `runner/main.py` читает `/candidate/prompt.md`, при наличии запускает `/candidate/prepare.py`, затем запрашивает один корректный ответ внутренней модели. При технической ошибке gateway выполняет до пяти повторов с тем же запросом. `prepare.py` получает через stdin JSON с `input`, `assets_dir: "/assets"`, `parameters`, `model`, `model_base_url` и `model_request_timeout`, затем возвращает JSON `{"context":"дополнительный контекст"}`. Модельные вызовы подготовки идут через переданный gateway с учётом токенов и теми же повторами; клиент использует переданный таймаут. Скрипт выполняется внутри одноразового контейнера; оценщик этот код не импортирует.

В немодельном режиме тот же образ запускает `/candidate/solve.py`. Скрипт получает `input`, `assets_dir` и, при наличии, `parameters`, возвращает JSON с `answer`. Длительность его работы ограничивает внешний `ARENA_RUNNER_TIMEOUT`. Решатель и метрика выбираются независимо: обычная программа может оцениваться как LLM-судьёй, так и вычисляемой метрикой. Формат метрики описан в [правилах оценки](public-evaluation.md).

По умолчанию одна модельная попытка может длиться до шести часов, подготовка — до 48 часов, весь запуск одного примера — до семи суток. HTTP-ожидание runner покрывает все шесть попыток gateway, паузы и запас на передачу результата. Оператор согласует эти пределы до кампании; клиентские таймауты должны покрывать допустимые повторы. Настройки описаны в [развёртывании](../deploy/README.md), ожидание — в [правилах долгих запусков](long-runs.md). Таймаут исполнения защищает от зависания и не задаёт лимит числа решений кампании.

Ресурсы решения измеряются обязательно, но не ограничивают поиск токенами. Время фиксирует доверенный runner снаружи контейнера, включая подготовку и повторы. Токены модельных запросов учитывает gateway по usage сервера в закрытом журнале конкретного запуска; утверждения кандидата о расходе не используются. Успешный модельный ответ без корректного usage считается ошибкой запроса. Для неудачных попыток без usage сохраняется `unreported_attempts`; известный расход является нижней границей. Для решения без модели доверенный runner фиксирует полный учёт с нулём токенов. Измерения судьи хранятся отдельно.

Для стороннего харнеса оператор собирает собственный образ с тем же stdin/stdout-протоколом и добавляет его в реестр до кампании. Реестр и версии адаптеров неизменяемы в рамках запуска. Разрешённый выбор между зарегистрированными харнесами или их параметрами является частью кандидата. Изоляция процесса не доказывает корректность эксперимента: ревьюер проверяет разрешённую область изменений и отсутствие подгонки под конкретные примеры.

## Необязательная измеряемая подготовка

Оператор может разрешить подготовку материалов до решения примеров: компиляцию, преобразование таблиц, построение индекса или другую часть метода. Она включается только для харнесов с `supports_build: true`. Встроенный runner поддерживает эту операцию; сторонний адаптер должен реализовать тот же контракт. Оценщик отвергает неподдерживаемую операцию до запуска контейнера.

В build-задании верхнеуровневое поле `operation` равно `"build"`, поля `input` нет. Runner запускает `/candidate/build.py` и передаёт JSON с `assets_dir: "/assets"`, `build_dir: "/output"`, `parameters`, `uses_model` и, при использовании модели, закреплёнными модельными настройками и gateway. Скрипт записывает результат в каталог вывода `/output` и возвращает JSON-объект. При успешном завершении runner возвращает `{"answer":"build complete"}`. Он не вызывает `solve.py` и не запрашивает окончательный ответ модели. Входы примеров и эталоны в подготовку не передаются.

Доверенный build-сервис получает неизменяемого зарегистрированного кандидата, запускает выбранный харнес, измеряет время и модельные обращения, затем публикует выходные файлы по digest. Квитанция версии 2 связывает digest кандидата, окружение исполнения, `input_assets_digest`, зависимости, результат и расходы. `input_assets_digest` описывает все закреплённые входные материалы любого типа; оператор задаёт его через `ARENA_INPUT_ASSETS_DIGEST`. Это не обязательно текстовая база знаний. Опубликованный результат следующего решения доступен только для чтения в `/assets/prepared`; `/output` существует только во время build.

Для харнеса с включённой измеряемой подготовкой кандидат с `build.py` должен иметь успешную квитанцию того же окружения и исходных материалов. Успешная подготовка и уникальные транзитивные зависимости учитываются один раз в суммарных расходах каждой оценки кандидата. Неудачи сохраняются; повторная доставка возвращает сохранённое состояние и не запускает сборку заново. Этот учёт не добавляет отдельного лимита решений.

## Необязательный выбор опубликованных материалов

При `supports_asset_selection: true` кандидат может перечислить неизменяемые материалы в `solution.json`: `parameters.asset_digests` — отсортированный список уникальных SHA256, не более 16. Оператор заранее подключает доверенное хранилище публикаций и общий журнал квитанций через `ARENA_BUILD_DIR`. Журнал обязателен даже для готовых весов и харнеса с `supports_build: false`: только доверенные связи публикаций с квитанциями позволяют отличить исходный материал от результата измеряемой подготовки. Все потребители одного хранилища используют тот же журнал; отдельный пустой журнал не заменяет существующую историю. Отсутствие или повреждение конфигурации и каталога связей считается ошибкой, а отсутствие связи конкретного digest в исправном журнале означает обычный импорт. Runner монтирует только выбранные материалы в `/assets/derived/<digest>`; неизвестные digest, подмена содержимого и запись в публикации отклоняются. Каталоги `derived` и `prepared` в корне исходных `/assets` зарезервированы подключёнными расширениями и не могут скрывать исходные файлы.

Publisher проверяет пути, размеры, типы файлов и hashes; он не выполняет код и сам по себе не измеряет создание содержимого. Через него можно импортировать разрешённые исходники, зависимости и веса. Результат измеряемой подготовки связан с квитанцией: повторное использование не позволяет обойти учёт его расходов. Кандидат, который использует такой результат, проходит собственную build-операцию, включая зависимости. Кампания определяет, какие преобразования относятся к методу и должны выполняться через build, а какие материалы разрешены как готовые входы.

Инструкции оператора и клиентские команды находятся в [развёртывании](../deploy/README.md). Эти возможности не требуют конкретного харнеса, модели, домена или MLflow.
