# MLflow

Законченные train-эксперименты, включая неудачные, сохраняются локально; MLflow подключается по выбору оператора. Public даёт только итоговый score кандидата: его можно сохранить с известными исследователю ID и конфигурацией. Закрытые данные, ответы и трейсы public/private не экспортируются в общее исследовательское хранилище. Адрес общего трекинга задаётся `MLFLOW_TRACKING_URI`, закрытого операторского — `ARENA_OPERATOR_MLFLOW_TRACKING_URI`. Адресов по умолчанию нет. Можно подключить один подходящий получатель или оба; без адресов остаётся локальная запись, SDK и очередь экспорта не используются.

Экспорт выполняет доверенный сервис либо используемый агент или харнес через SDK. Общий получатель принимает train и только разрешённые public-метаданные со score. Полные public/private-результаты допустимы лишь у отдельно настроенного операторского получателя с закрытым доступом. Private никогда не перенаправляется в общий трекинг при отсутствии операторского URI. При недоступном сервере сохрани очередь экспорта и отметку `tracking_pending`; сбой трекинга не повод повторять решение примеров. Журнал кампании остаётся источником порядка кандидатов и их родословной, MLflow связывается с ним через ID. Повтор экспорта не создаёт новое решение и не расходует лимит кандидатов.

## Доступ исследователя к train-трейсам

Если кампания использует MLflow для train-измерений, исследователь должен иметь доступ к содержимому их трейсов через общий сервер из своей рабочей среды. Оператор передаёт разрешённый `MLFLOW_TRACKING_URI` и доступ к чтению, включает экспорт train и запись модельных вызовов по [инструкции развёртывания](../deploy/README.md). Только операторский URI, доступный UI или успешная отправка метрик не подтверждают эту готовность. Обязательность MLflow задаётся условиями кампании; если он обязателен, локальная запись не заменяет доступ к трейсам.

1. После завершения train-проверки возьми `tracking.shared.run_id` из её результата. В UI общего MLflow открой experiment `arena-train/<case_id>` и этот run. Если ID ещё неизвестен, найди run по тегам `split=train`, `campaign_id` и параметру `candidate_id`; проверь `subset_id` и `conditions_id`, чтобы не смешать разные замеры.
2. Открой связанные с run трейсы. Через SDK тот же путь — `MlflowClient(tracking_uri=...).search_traces(locations=[experiment_id], run_id=run_id, include_spans=True)`. Читай входы, выходы, ошибки и времена spans; `role` и `example_id` связывают их с решателем, судьёй и train-примером. Артефакт `record.json` содержит ответы, оценки и расходы; для файловых трейсов он ссылается на артефакты `calls/`.
3. Сохраняй в findings ссылку на run и ID нужного трейса вместе с `example_id` и выводом. При `tracking_pending` используй сохранённые train-артефакты и сообщи о недоставленных трейсах; доверенный экспортёр повторяет очередь без повторного решения. Не переключайся на закрытый операторский сервер ради поиска недостающих данных.

При подготовке такого экспорта проверь весь путь на синтетической train-записи с подставными вызовами: экспорт, поиск run и чтение payload трейса из среды с исследовательскими правами. Запиши в `preparation.md` общий URI без секретов, experiment/run/trace ID и результат чтения. Перед стартом и возобновлением поиска повторно прочитай эту запись через исследовательский доступ. Для немодельного решения проверяются записанные шаги и их результаты; модельные вызовы не выдумываются. Проверка не использует реальные модели, public/private-данные и не расходует private-допуск.

## Что сохранять

Один run соответствует проверке кандидата на конкретном наборе. Параллельные исследователи используют отдельные процессы и run ID.

| Поле | Содержание |
| --- | --- |
| `campaign_id`, `case_id`, `candidate_id` | Кампания, кейс, кандидат |
| `candidate_digest`, `revision`, `parent_ids` | Неизменяемый пакет, ревизия кода и все родители, включая неудачные решения |
| `proposal_index`, `hypothesis`, `change` | Номер предложенного решения, гипотеза и смысл изменения |
| `model`, `harness`, `harness_version`, `parameters` | Реальная конфигурация кандидата; модель отсутствует у немодельного решателя |
| `metric_version`, `direction` | Версия замороженного пакета метрики, направление `maximize` или `minimize` |
| `split`, `dataset_id`, `dataset_version`, `subset_id`, `conditions_id` | Части данных и условия сопоставимости; train и public не смешиваются |
| `proposed_at`, `started_at`, `completed_at` | Моменты предложения, начала и завершения для восстановления параллельного поиска |
| `status`, `error` | Результат проверки или явный сбой; ошибка не превращается в выдуманную оценку |

Для train дополнительно сохраняются состав подвыборки, версия эталона, ответы, оценки критериев, вызовы, инструменты, трейсы и решение «оставить/отклонить». Ресурсы каждого примера хранятся отдельно для `solver` и `judge`: `wall_seconds` и `usage` с `prompt_tokens`, `completion_tokens`, `total_tokens`, `attempts`, `unreported_attempts`. Итоговые `solver_tokens`, `solver_seconds`, `solver_unreported_attempts` и аналогичные `judge_*` обязательны. Расходы агрегации хранятся отдельно и включаются в итоговые `judge_*`. Время включает подготовку и повторы. При неизвестном usage сумма является нижней границей; нулевые токены немодельного решения означают полный учёт, а не отсутствие измерения. Стоимость в валюте может оставаться `null`.

Отсутствие usage и ошибка содержательного ответа — разные состояния. Корректный ответ без достоверного usage сохраняется без повторной генерации, а попытка увеличивает `unreported_attempts`. Gateway сохраняет безопасную диагностику стадии ошибки, HTTP-статуса и идентификаторов запросов; тексты исключений и тела ошибочных ответов в диагностические поля не копируются. Точные токены потерянной попытки можно восстановить только по достоверному учёту upstream. Токенизация входа или расход следующего успешного повтора не заменяют такой учёт.

Public-run содержит только доступные исследователю метаданные кандидата и итоговый score. Не добавляй к нему закрытые ID примеров, расходы выполнения, оценки критериев, ответы, ошибки с содержимым данных или трейсы. Условия сопоставимости серии задаются кампанией. Отсутствующие измерения не заменяются нулями.

На пример сохраняется один корректный ответ решателя. Порядок оценки и число голосов определяет пакет метрики; у встроенного профиля `llm` это поле `votes`. Записывай фактические обращения и расходы собственной модельной метрики, включая агрегатор. Технические повторы записываются отдельными попытками с прежними входом и настройками. Для вычисляемой метрики записываются её результат, версия и время, без искусственных судейских вызовов. Перед экспортом исключи секреты и заголовки авторизации. Полный `model_base_url` запуска тоже секретен: путь `/runs/<run_id>/<capability>/v1` содержит допуск к учёту. Удаляй `capability` из URL, входов инструментов, трасс HTTP, ошибок и остальных полей до их записи или экспорта. Экспортёр дополнительно очищает известные форматы секретов, но это не заменяет проверку содержимого перед публикацией.

Порядок кандидатов, родство, остановка поиска и выгрузка кривой/AUC описаны в [журнале поиска](search-history.md). MLflow не заменяет этот журнал. Разные подвыборки или условия не объединяются в одну сопоставимую кривую.

## Подключение и повтор экспорта

Установи необязательную зависимость в экспортирующее окружение: `uv sync --frozen --extra tracking`. Для контейнерного образа включи build-аргумент `ARENA_TRACKING=true`; базовому runner и gateway MLflow не нужен. URI и доступы задаются окружением оператора, а не кодом кандидата. Сервисы экспортируют уже сохранённый результат; ошибка экспорта не отменяет полученный ответ или оценку.

```bash
uv run --extra tracking python -m evaluator.tracking export train_record.json
uv run --extra tracking python -m evaluator.tracking flush --queue /srv/arena/tracking/shared
uv run --extra tracking python -m evaluator.tracking export private_record.json --operator
```

`export` требует URI выбранного получателя. `--operator` выбирает закрытый URI и отдельную операторскую авторизацию. Для `export` можно указать `--queue`; по умолчанию используется `.tracking` рядом с записью. `flush` обрабатывает сохранённую очередь без повторного запуска решений и судейства; путь очереди должен совпадать с использованным при экспорте.

Для сервисов `evaluator.tracking.export_configured(record_path, queue_dir=None)` выбирает только настроенные получатели и возвращает их квитанции. Без URI возвращается пустой словарь. По умолчанию очереди лежат рядом с записью в `.tracking/shared` и `.tracking/operator`; при переданном `queue_dir` — в его подкаталогах `shared` и `operator`. Private требует операторского URI, если экспорт включён; отсутствие такого URI не разрешает общий экспорт. Каждая очередь сохраняется до подтверждённой публикации, повтор экспорта не создаёт новое решение.

Запись содержит `split`, `params`, числовые или `null` значения `metrics`, `status: "FINISHED"` или `"FAILED"`, список `calls` и временные поля `start_time_ns`/`end_time_ns` в Unix nanoseconds. Вызовы содержат `name`, `inputs`, `outputs`, `attributes`, `status: "OK"` или `"ERROR"` и свои временные поля. Атрибуты связывают span с примером, ролью, критерием и голосом; секреты исключаются. Исходные времена сохраняются в трейсах, а время публикации не заменяет длительность эксперимента.

Встроенный судья `kind: llm` сохраняет в train отдельный `LLM` span `judge_model` на каждую фактическую попытку с атрибутами `role`, `example_id`, `criterion`, `vote` и `attempt`. Промпт и модельный ответ очищаются от секретов; при транспортных ошибках сохраняется безопасная диагностика без тела ошибочного HTTP-ответа. Ошибка записи трейса отмечается в `trace_errors` и не вызывает новый модельный запрос. При повторном использовании готового результата на train-подвыборке сохранённые попытки переносятся в её run без повторного судейства.

Для длительного исследовательского запуска используй компактную запись с `calls: []` и `call_files`: списком абсолютных путей к неизменяемым JSON-файлам отдельных вызовов. Экспортёр читает и очищает по одному файлу, сохраняет собственные снимки в `calls/` внутри очереди и публикует каждый вызов отдельным трейсом того же run. Полные payload сохраняются как артефакты `calls/`; `record.json` ссылается на их имена. Расход памяти зависит от крупнейшего вызова, а не от суммарного объёма истории. При наличии `params.role` это значение задаёт роль внешних вызовов. Исходные `span_id`/`parent_id` сохраняются в атрибутах; вложенную структуру небольших проверок по-прежнему задаёт встроенный список `calls`.

Подтверждение отдельного вызова требует прочитать его payload из MLflow: успешный `flush` или одна metadata ещё не означают доставку. Стабильный тег включает ID экспорта и порядковый номер вызова, поэтому повтор продолжает недоставленные вызовы, а одинаковые попытки остаются разными трейсами. Получатель помечается завершённым только после всех вызовов; отказ другого получателя не отменяет эту квитанцию. `flush` работает со снимками очереди и не требует исходных файлов или повторного запуска исследователя. Перед каждой недоставленной публикацией содержимое файла повторно очищается с текущим набором известных секретов; артефакт и span получают одинаковый очищенный payload. Это не изменяет ID вызова и не удаляет ранее опубликованные сведения. Очередь и её `calls/` нужно сохранять вместе.

`arena_execution_status` сохраняет исходный статус выполнения отдельно от состояния публикации: исключение экспортёра может пометить MLflow run как `FAILED`, хотя исследователь завершился штатно. `arena_export_complete` становится `true` только после полной доставки. При переходе со старой монолитной записи на manifest монитор использует отдельную очередь и новый run; прежняя неудачная публикация сохраняется как свидетельство сбоя и не переписывает историю выполнения.

Теги, параметры и метрики run, включая подтверждение завершения экспорта, записываются синхронно даже при `MLFLOW_ENABLE_ASYNC_LOGGING=true`. Ошибка записи оставляет экспорт в очереди; переключение получателя и восстановление его учётных данных происходят после завершения этих запросов.

## Закрытые результаты

Public/private задания, эталоны, ответы, отдельные оценки, промпты и трейсы остаются в закрытом хранилище оценщика. Названия экспериментов, теги и скрытые URL не разграничивают доступ.

Private API возвращает исследователю только статус, включая завершённый финал. Оценки, ресурсы и выбранные лучшие решения смотрит оператор в закрытом результате. Private автоматически не попадает в поиск, общий MLflow или график эволюции; завершение кампании само по себе не разрешает экспорт. Операторский экспорт требует отдельного закрытого получателя.
