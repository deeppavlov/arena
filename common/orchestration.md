# Мультиагентная работа

Оркестрация выполняется обычным чатом или доступными субагентами. Отдельный SDK, конкретный харнес, tmux и несколько машин не обязательны. Если параллельных агентов нет, роли выполняются последовательно с теми же файлами передачи контекста.

Оркестратор держит постановку, карту направлений, счётчик решений и принятые решения. Он поручает анализ, реализацию и замеры работникам, получает короткие выводы со ссылками и читает полный train-трейс для конкретного спорного вопроса. Исследовательские агенты и тестируемый решатель — разные роли. Решатель может обходиться без модели, харнес может быть предметом поиска в разрешённых промптом пределах. Все роли применяют [правила долгих запусков](long-runs.md): тишина сама по себе не повод прервать работника.

| Роль | Ответственность | Результат |
| --- | --- | --- |
| Оркестратор | Постановка, лимит предложений, распределение работы, остановка, отбор входа private | Состояние кампании и основания решений |
| Эксперт по постановке | Проверить входы, метрику и допустимые изменения | Пробелы и проверяемая постановка |
| Исследователь | Гипотеза в выданной области; реализация, замеры и анализ | Кандидат, родословная и findings, включая отрицательные |
| Независимый ревьюер | Проверить сопоставимость, утечки, подгонку и альтернативные объяснения | Вывод с конкретными свидетельствами |
| Закрытый оценщик | Выполнить public/private-проверки и соблюдать границу обратной связи | Public-score агенту, private-результаты оператору |

До поиска эксперты проверяют постановку, измеритель и исходные решения. Число работников определяется независимыми направлениями и доступным параллелизмом; одинаковую работу не дублируют ради числа агентов. Ревьюер по возможности не оценивает собственную реализацию.

Рабочая память кампании хранится в `runs/<campaign>/`:

- `campaign.md`: цель, версии данных и метрики, направление улучшения, фиксированные условия, разрешённые промптом изменения, лимит решений, точные размеры входа и выхода private, текущее состояние.
- `board/claims/<agent>.md`: гипотеза, механизм, область изменений, ожидаемый эффект, опровергающая проверка, worktree и состояние.
- `board/findings/<agent>.md`: ID и ревизия решения, набор, ссылки на замеры, результат, ограничения, причина неудачи и рекомендация.
- Журнал по [search-history.md](search-history.md): каждое предложение, родители, неизменяемый снимок, проверки, остановка, данные кривой и AUC.
- `selection.md`: доступные свидетельства, обоснование полезности каждого финалиста и весь замороженный входной список.

Git сохраняет содержимое реализаций. Журнал явно хранит родство идей: несколько родителей допустимы и не обязаны совпадать с родителями Git-коммита. Комбинация подходов или изменение разрешённых параметров — новое решение. Технический повтор проверки прежнего снимка нового решения не создаёт.

У каждого исследователя отдельная ветка и worktree либо отдельная копия. Его область записи задана явно; общие настройки, метрика и чужие файлы не меняются. До разделения веток сохраняется исходная ревизия. Каждая передача задачи содержит цель, scope, исходную ревизию, доступные данные, фиксированные условия, разрешённые изменения, доступные места в лимите решений и ожидаемый файл результата. Работник сначала читает claims/findings, затем заявляет свой механизм. При пересечении гипотез оркестратор объединяет работу либо разводит проверки.

Оркестратор согласует регистрации через единый журнал: суммарное число предложений всех работников не превышает лимит. Учитываются неработающие решения и неудачные замеры; они не исчезают из истории и могут иметь потомков. Лимит числа решений не ограничивает токены или время поиска. Ресурсные замеры при этом обязательны.

Для каждого долгого задания сохраняй ID процесса или задания кластера, пути прогресса и результатов, время запуска и расчёт следующего ожидания. После первого полного примера проверь исправность, рассчитай оставшуюся длительность и ожидай её целиком. Прогресс пишет процесс; для субагентов используй штатное ожидание завершения. Пользователю можно рекомендовать увеличить время жизни и глубину вложенности агентов, если среда это позволяет.

После каждой проверки работник сохраняет findings и кратко возвращает: **что проверено → что получилось → что опровергнуто → что делать дальше**. Неудачи не удаляются. Смена направления согласуется с оркестратором, чтобы работники не начали одинаковый поиск.

До изменения записывается предсказание; эффект проверяется за пределами исходного примера; учитываются регрессии, все предложения и простой baseline. Сопоставимые измерения выделяются по набору и условиям. Авторитет агента, объём кода и потраченное время не заменяют свидетельства.

## Завершение поиска

Планируй воронку с самого начала под точное число входных финалистов. Проверки устойчивости, сравнительные замеры и независимое ревью выполняются в ходе поиска. Агент выбирает дизайн train-валидации; при пустом public обязательной публичной проверки нет. Public раскрывает только общий score; private не является источником обратной связи.

При достижении лимита перестань регистрировать новые решения, продолжи плановые проверки уже предложенных. При явной команде человека остановить поиск запиши остановку в журнал, сообщи всем работникам и запрети новые предложения и проверки, включая ожидающие запуска. Дождись только уже выполняющихся проверок. Не начинай дополнительные замеры, доработку кандидатов или новый цикл ревью после этой команды. Чтение сохранённых результатов и формирование отбора разрешены.

По накопленным свидетельствам выбери ровно заданное число различных решений. Качество — один из факторов наряду с разнообразием, устойчивостью, риском переобучения и полезностью закрытой проверки. Не заменяй этот выбор автоматическим top-K и не дополняй список дубликатами. Зафиксируй причины выбора каждого кандидата. Далее следуй [промпту финалистов](../prompts/finalists.md): один замороженный пакет, одна приватная серия и точное число лучших решений для оператора.
