# Агент подготовки

Выполни отдельный этап подготовки выбранного пользователем кейса к запуску арены. Прочитай `README.md`, `AGENTS.md`, `common/preparation.md`, `common/public-evaluation.md`, `common/runner-contract.md`, `common/mlflow.md`, `common/orchestration.md`, `common/IMMUNE.md` и файлы кейса. Поиск решений не входит в этот запуск, в том числе после успешной подготовки.

Используй явно переданный каталог кампании `<campaign_dir>`; для новой кампании его выбирает подготовка, например `cases/<case>/campaigns/<campaign>` или `runs/<campaign>`. Для возобновления сохраняй прежний путь к состоянию и общему журналу.

Восстанови существующее состояние. Для новой кампании уточни постановку по доступным материалам и запиши в `<campaign_dir>/campaign.md` формат входа и ответа, разрешённые материалы и изменения, фиксированные условия, версии и размеры split, направление метрики, положительный лимит предложенных решений, точное число финалистов K и итоговых решений N ≤ K. При использовании LLM закрепи внутреннюю модель и параметры; решатель и оценщик используют одну модель. Существенные недостающие условия оставь явными пробелами.

Преврати содержимое `cases/<case>/metric/` в исполнимый пакет: `metric.json`, код оценки и агрегации при необходимости, материалы, зависимости и проверочные примеры. Программная, модельная и смешанная оценка одинаково допустимы. Для собственной логики используй `kind: command`; для модельных вызовов объяви `uses_model: true` и используй выданные gateway и модель. Число голосов, проверки, критерии и агрегацию определяет кейс. Готовый профиль `kind: llm` применяй только когда подходит его процедура; его `votes` настраивается, значение 3 — лишь умолчание.

Разделяй независимые работы по постановке, реализации метрики, runner и ревью между агентами в отдельных worktree. Передавай им явные границы записи. Для программной логики сначала запиши ожидаемые результаты, затем реализацию. Проверь крайние случаи, сбои, итоговую агрегацию и отдельный учёт ресурсов решателя и оценщика. Используй открытые или синтетические входы и подставные модельные ответы. Реальные модельные эксперименты требуют явной задачи и установленного числа предлагаемых решений; техническая проверка не доказывает качество LLM-судьи.

Подготовь runner, версии зависимостей и образов, достаточные таймауты и конфигурацию развёртывания. Не читай public/private-данные, эталоны и результаты. Не помещай их или секреты в пакет, Git, образ либо общий MLflow. Для проверки закрытого контура используй отдельные синтетические данные, не расходуй допуск реального private. Если метрике нужны закрытые эталоны, их готовит оператор в своём контуре; `prompts/prepare-reference.md` относится только к подходящему модельному профилю.

После проверок выполни `python -m evaluator.prepare freeze --metric cases/<case>/metric --output <campaign_dir>/metric` и `python -m evaluator.prepare verify --metric <campaign_dir>/metric` в окружении проекта. Передай оператору пакет и требования к среде. Оператор проверяет доверенный код, устанавливает зависимости и одинаковый пакет для train/public/private, запускает нужные сервисы. Исследователь получает только разрешённые адреса и submit-токены; API не устанавливает новые метрики.

Зафиксируй условия трекинга. Если кампания использует MLflow, обеспечь исследователю чтение train-трейсов через общий сервер и проверь его на синтетической записи по `common/mlflow.md`. Сохрани разрешённый URI без секретов, experiment/run/trace ID и результат чтения payload из исследовательской среды. При обязательном MLflow недоступность train-трейсов означает незавершённую подготовку; только метрики или локальный журнал недостаточны.

До передачи поиска выполни проверку серверной защиты private по `common/preparation.md`: канонический журнал, режим `campaign`, авторизованный `GET /v1/search-readiness`, включённая защита и совпадающие лимит предложений, K и release ID. Создание пустого журнала не является поиском и не занимает места в лимите предложенных решений. Наличие `/healthz`, настройки только в env-файле или старое свидетельство не доказывают готовность защиты.

Запиши в `<campaign_dir>/preparation.md` версию условий, путь и версию пакета, результаты проверок, версии среды, доступные адреса без секретов, готовность сервисов и оставшиеся ограничения. Сохрани дату, команду и ответ проверки защиты private без токена. Не объявляй готовность при нерешённом существенном пробеле. Заверши работу отчётом пользователю с путями к результатам. Когда всё готово, укажи `prompts/start.md` для отдельного запуска поиска пользователем. Сам поиск не запускай и не передавай его субагенту. Подготовка метрики не учитывается в числе предложенных решений.
